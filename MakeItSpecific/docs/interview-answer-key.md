## 阶段 0：开场 & 自我介绍

### Q0.1 用 2 分钟介绍项目

**答题思路**：别念 README。按「定位 → 和 ChatGPT 的区别 → 架构一句话带 2-3 个技术名词 → 一个难点+解法 → 一个实感成就」五段式，留钩子让面试官往下追。

**参考答案**：
> 我做的是一个 AI 工作流增强 Agent，叫 Alfred。它解决的是：很多人有个模糊想法——比如"我想做个论坛"——但不知道怎么一步步落地。ChatGPT 是被动问答，你问一句它答一句；Alfred 是主动引导——先判断你给的信息够不够，不够就追问，够了就把想法变成一份结构化"任务契约"：目标、范围、约束、验收标准，甚至在你踩"硬编码密钥""生产库删数据"这类坑之前给你工程规范预警。
>
> 技术栈是 FastAPI + LangGraph。我用 LangGraph 建了状态机图，一条消息走十来个节点：意图识别 → 上下文增强 → RAG 检索 → Planner 判断完整度 → 要么追问、要么执行。执行层是 ReAct agent，能调工具查我本地知识库。检索做的是混合检索：稠密向量 + 稀疏全文 + RRF 融合 + rerank 精排。记忆做了三层上下文——最近原文、滚动摘要、语义事实——防止长对话丢关键约束。
>
> 最难的点是 LLM 的非确定性，没法用传统断言测。我的策略是"测确定性部分、监控非确定性部分"：维度合并、JSON 解析、降级逻辑用单测覆盖，语义漂移、幻觉靠图里 checkpoint 和 reflect 两个质检节点兜底。
>
> 最有成就感的是把它从一个大项目的子模块，独立成了 Docker 自包含、nginx 统一路由的可部署服务，过程中踩了不少真坑——子图 ReAct 的 token 流式不冒泡、稀疏检索的 GIN 索引建错字段，都是自己 debug 出来的。

**答题思路**：考"一句话产品定位"。抓住"主动引导 vs 被动问答"这个核心差异。

**参考答案**：
> Alfred 是通过引导式对话 + 工具调用，把用户模糊的想法变成可执行方案的个人 AI 助手。和 ChatGPT 最大的区别是：ChatGPT 是被动问答，你问什么它答什么；Alfred 会主动判断信息够不够、不够就追问、够了就产出结构化契约，还带工程规范预警和三立场建议，把"决策权"和"执行边界"都帮用户理清楚。

### Q0.3 你独立负责的部分和最有成就感的一点

**答题思路**：开放式，但要有"技术含量 + 量化结果"，别说"我写了代码"。

**参考答案**（一种答法）：

## 阶段 1：项目概述

### Q1.1 为什么独立出来，带来哪些结构变化

**答题思路**：考你是否理解"独立"背后的工程动机（解耦、可独立部署），不是"我想独立就独立"。

**参考答案**：
> 它原本是 Portal 多项目入口里的一个子项目，但 Portal 只管编排和路由，Alfred 的业务逻辑是独立的，混在一起部署和配置都耦合。独立后：config 不再读 Portal 层的 `../.env`，只读项目根 `.env`；docker-compose 自带 postgres（pgvector）实现完全自包含；服务名从 `specific-api` 改成 `alfred-api`、库名从 `chatdemopg` 改成 `alfred`，避免和其他子项目冲突。本质是"解耦入口、独立部署"。

### Q1.2 技术选型为什么这样选

**答题思路**：每个选型一句话说"它在架构里的角色 + 为什么不用替代品"，别背清单。

**参考答案**：
> FastAPI 因为要异步 + SSE 流式；LangGraph 因为我要的是一个带条件路由和重试回环的状态机图，不是顺序脚本；LangChain 主要用它的模型抽象和 `create_react_agent` 预构建，省掉手写 ReAct 循环；PGVector 因为一张实例同时扛向量检索、会话持久化、用户画像三件事，少维护一个组件；DashScope 因为 embedding（text-embedding-v4）、rerank（qwen3-rerank）、LLM 一家齐了。如果要重选，LangChain 是我最想换的——抽象层太厚、版本 churn 大，现在更倾向直接基于 LangGraph 自己写薄封装。

### Q1.3 一条消息从进来到输出的完整流程

**答题思路**：完整画图，**别漏 planner 之后**（这是最常见的翻车点）。

**参考答案**：
> `router → enrich → rag → planner → {clarify | engineering_check} → {execute | multi_agent} → checkpoint → {reflect | execute} → END`。router 判意图、enrich 透传增强 query、rag 被动注入知识、planner 判断信息完整度——不够走 clarify 追问、够走 engineering_check 工程规范检查；engineering_check 正常放行到 execute（ReAct 执行）或 multi_agent（三立场），阻断就直接 END；execute/multi_agent 后进 checkpoint 查语义对齐，对齐了进 reflect 查质量，不过关回 execute 重试（有次数上限），最后 END。

## 阶段 2：架构与核心设计

### Q2.1 为什么用 LangGraph 而不是 while 循环

**答题思路**：核心是"显式状态 + 条件路由 + 循环重试 + 可观测"。别答"耦合低"（图节点靠共享 state 是强耦合）。

**参考答案**：
> 手写 while 循环，路由分支、状态传递、重试回退都得自己维护，代码会越来越乱。LangGraph 给了四样东西：一是显式的共享状态 `AgentState`，节点读写它、自动在节点间传递；二是条件路由 `add_conditional_edges`，下一步去哪由函数决定而不是一堆 if；三是循环重试，我的 checkpoint→execute、reflect→execute 就是靠图边串起来的，带次数上限；四是可观测可恢复，状态能检查、能注入。这些手写 while 都要自己造轮子。

### Q2.2 AgentState 挂了哪些字段

**答题思路**：别掉进"哪些是节点私有变量"的坑——LangGraph 里 state 是全局共享的。答两个真区别：`messages` 用 reducer 追加、其余覆盖；以及"生命周期短"的字段。

**参考答案**：
> `AgentState` 是个共享状态字典，字段有：messages、module、background、extra_context、expressed_dimensions、clarify_round、plan、rag_context、enriched_query、tool_results、output、reflection_count、intent，还有三层上下文（l1_raw/l2_summary/l3_facts/last_turn_summary/turn_count）、工程规范（engineering_context）、多 Agent（multi_agent_perspectives/synthesis）、checkpoint 反馈（checkpoint_feedback/checkpoint_retry_count）、执行进度（completed_steps/execute_round）、以及 user_id/session_id。关键点：没有严格意义的"节点私有变量"——state 就是共享机制。真正的区别有两处：`messages` 是唯一用 reducer（add_messages）**追加**的字段，其他字段写就整体覆盖；有些字段只是"生命周期短"，比如 checkpoint_feedback 只在质检回环里短暂存活。

### Q2.3 为什么分三层上下文

**答题思路**：答对 L1=窗口、L2=滚动摘要、L3=事实（别反），再答核心动机"防遗忘 + 防幻觉"。

**参考答案**：
> L1 是最近 3 轮原文，保证当前对话流畅；L2 是滚动摘要，覆盖全部历史但压缩过；L3 是语义事实，从每轮提取原子偏好/决策/约束，按需召回。分三层有两个动机：一是省 token——全塞原文窗口塞不下长历史；二是防遗忘 + 防幻觉——长对话里关键约束（比如"不要用 Redux"）如果不单独沉淀成 L3 事实，模型要么忘了、要么凭印象编。只用一层"最近 10 轮"，长对话超窗口后关键约束就丢了。

### Q2.4 多 Agent Panel 是什么，和 ReAct 什么关系

**答题思路**：考你是否真读过 `multi_agent.py`。两个易错点：不是"温度调整"、不是"ReAct 指挥它们"。

**参考答案**：
> 三立场 Panel 是三个**不同的 System Prompt**——实用派（最快落地）、稳健派（安全可维护）、创新派（差异化），用 `asyncio.gather` **并行**跑，最后第四个 LLM（阿福 synthesizer）把三方输出整合成结构化对比（共识/分歧/代价/决策点）。触发是硬约束：用户明确要求多角度对比，或低置信度且用户拒绝追问。它和 execute 是**并列节点**——都从 engineering_check 分出来、都汇到 checkpoint，谁也不是谁的"指挥"。

## 阶段 3：项目拷打

### 3.1 上下文引擎

**Q3.1.1 内存字典算持久化吗，什么时候丢？**

**答题思路**：核心是"易失缓存 vs 真持久"的区分，丢失时机别答成"覆盖"。

**参考答案**：
> 不算，它是易失缓存。真正持久的是 PGVector 那一路。丢失有两个时机：一是**进程重启整体丢**——这是"不持久"的本质；二是运行时靠 LRU 驱逐——每个 session 最多 50 条事实、全局最多 500 个 session，超了就把最旧的 session 挤掉。所以"双路径持久化"这个说法其实不严谨，只有一路是持久化的。

**Q3.1.2 L3 事实以什么粒度存储？**

**答题思路**：讲清"一轮一行 → 一条一行"的演进 + 为什么。

**参考答案**：
> 现在是"一条事实 = 一行"：每条原子事实单独一个 document、单独一个 embedding、单独一个 id（`session_id:turn:index`）。这是后来改的——一开始是"一轮 = 一行"，把整轮提取的所有事实用换行拼成一个文档、打一个 embedding。问题在于检索粒度太粗：一个向量是整轮事实的混合语义，召回时整轮一起出来，单条事实特征被稀释，也没法独立删改。改成细粒度后语义召回直接命中单条事实，代价是同一轮从 1 次 embedding 变 N 次，但 `embed_documents` 支持批量，一次调用全算完，成本可控。

**Q3.1.3 embedding 挂了，L3 提取和召回会怎样？**

**答题思路**：两处都要答对——提取降级规则、召回降级关键词，别编"预算 cosine"。

**参考答案**：
> 提取侧，LLM 提取失败会降级到**正则规则提取**（`_extract_atomic_facts`），靠"我用/我喜欢/不要/必须"这些模式抓事实，不是直接挂掉。召回侧，embedding 挂了根本算不出向量，所以降级到**内存字典的关键词匹配**（`_retrieve_facts_memory`）。整体是"降级不崩溃"，只是精度下降。

**Q3.1.4 话题切换中间地带真的调了 LLM 精检吗？**

**答题思路**：⚠️ 这是"注释写了、代码没实现"的典型。诚实点破。

**参考答案**：
> 没有。代码里重叠率落在中间地带（0 < overlap < 0.3）时，注释写了"未来可加 LLM 精检"，还留了一段示例 prompt，但实际逻辑是**保守处理、不重置摘要**（直接 return False）。所以这个"两级检测"实际只有 keyword 快检这一级在跑，LLM 精检是没落地的 TODO。

**Q3.1.5 LRU 驱逐阈值和 bug**

**答题思路**：⚠️ 考你是否真读过代码、有没有发现 bug。这是"诚实 + 细节"双重加分题。

**参考答案**：
> 阈值是全局最多 500 个 session（每个 session 最多 50 条事实）。原来 `_evict_old_sessions_locked` 末尾有一行残留的 `return "\n".join(lines)`，但 `lines` 这个变量在方法里根本不存在——所以一旦 session 数超过阈值、驱逐循环跑完，就会抛 `NameError`。这是我后来读代码时发现的，单用户场景要攒到 500 个 session 才会触发，属于潜伏 bug。

**Q3.1.6 "跨会话可用"和按 session_id 过滤矛盾吗？**

**答题思路**：⚠️ 注释和代码不一致，直接点破。

**参考答案**：
> 矛盾。`_retrieve_facts` 的 docstring 写的是"跨会话可用"，但实际检索时 `filter_meta={"session_id": ...}` 是按当前 session 过滤的，所以是**会话隔离**，不是跨会话。这是个注释和实现不一致的地方——L3 事实只在当前会话内召回。

**Q3.1.7 L2 滚动摘要怎么增量更新？**

**答题思路**：讲清"旧摘要 + 本轮 → 新摘要"，以及为什么不全量重建。

**参考答案**：
> 每轮结束后，把「已有摘要 + 本轮新内容」一起喂给 LLM，生成新的滚动摘要，不是每次拿全量历史重建。因为全量历史越来越长，重建的 token 成本和延迟会线性涨；增量更新只处理增量，有 256 token 的摘要上限（用 `max_chars = max_summary_tokens × 3` 粗略控制）。

### 3.2 RAG 检索

**Q3.2.1 dense 和 sparse 作用在什么文本上，为什么不一样？**

**答题思路**：讲清两段文本的构成 + "语义 vs 词面"的分工。

**参考答案**：
> dense 的 embedding 作用在 `search_text_dense` 上，它 = source_title + category + 实体名 + section_title + body，把来源信息和正文一起喂给向量模型，抓**语义相似**；sparse 作用在 `search_text_sparse` 上，它 = repository + url + author + category + 实体名，只放专有名词和元数据，抓**精确词面匹配**。两段文本不一样，是因为两者目标不同：一个要"意思像"，一个要"字面准"。

**Q3.2.2 RRF 原理，为什么不用归一化加权？**

**答题思路**：公式 + "只看排名不看分数"这个核心。

**参考答案**：
> RRF 是倒数排名融合，`RRF(doc) = Σ 1/(k + rank)`，k 取 60。它的核心是**只看排名、不看绝对分数**。dense 的 cosine 和 sparse 的 ts_rank 尺度完全不同，直接加权求和得先归一化，而归一化对异常值敏感；RRF 用排名，天然免疫尺度差异，只要"你在两路里都排得靠前"，分数就高，所以更稳。

**Q3.2.3 rerank 和 embedding 的原理区别，为什么只对 top-20 做？**

**答题思路**：双塔 vs 交叉编码器，这是必考。

**参考答案**：
> embedding 是双塔模型，query 和 doc 各自独立编码成向量再算余弦，快、能预计算建索引，但两者之间没有 token 级交互；rerank（qwen3-rerank）是交叉编码器，把 query+doc 拼成一条输入一起过 transformer，token 直接互相 attention，精度高但每一对都要现算、无法预计算。所以只能"双塔粗召回 + 交叉编码器精排"——只对粗排 top-20 做 rerank，用慢而准的模型去兜快而粗的模型。

**Q3.2.4 score 是什么尺度，sparse-only 文档能过 0.6 吗？**

**答题思路**：⚠️ 尺度陷阱，这是最难的题之一。核心是"RRF 后 score 保留第一路的尺度"。

**参考答案**：
> 这是个尺度陷阱。RRF 融合时 `doc_map` 保留的是**第一次出现那路**的原始 dict，而 dense 在 sparse 前面，所以一个同时被两路召回的文档，它的 `score` 是 cosine（0~1）。但**只被 sparse 召回、没被 dense 召回的文档**，`score` 是 ts_rank——通常远小于 0.6——所以它过不了 `score≥0.6` 的门，只能靠 `rerank_score≥0.3` 被捞回来。也就是说稀疏通道的贡献主要体现在"提升 RRF 排名"，而不是"独立通过阈值"。

**Q3.2.5 BM25 实际是什么，GIN 索引生效吗？**

**答题思路**：⚠️ 双重名不副实。诚实点破，展示你读到了底层。

**参考答案**：
> 两处都不对。一是"BM25"其实是 PostgreSQL 的 `ts_rank`，不是 BM25 公式。二是 GIN 索引建在 `to_tsvector('simple', document)` 上，但我的 `_sparse_search` 查的是 `metadata->>'search_text_sparse'`，两个表达式不一样，**GIN 索引对稀疏检索不生效**，等于每次全表扫描 + 现场算 tsvector。而且那个有索引的 `bm25_search`（查 document 字段）根本没被 V5 检索调用。

**Q3.2.6 语义分块断点怎么找？**

**答题思路**：讲清"相邻句 cosine < 0.5 就是断点" + 全高于阈值时的兜底。

**参考答案**：
> 先按标题切 section，再按标点切句，然后对相邻两句算 cosine 相似度，相似度 `< 0.5` 的位置就是语义断崖，作为断点。如果整段相邻句相似度都高于 0.5，就没有断点，靠 `max_chars=800` 的硬切兜底，避免超长块。

**Q3.2.7 关键词加权对中文生效吗？**

**答题思路**：⚠️ 又一个"正则漏了 CJK"的坑。

**参考答案**：
> 不生效。`_apply_keyword_boost` 用的 `_extract_tech_terms` 只有 4 组英文正则（PascalCase、连字符、全大写、点分），**没有中文正则**。而语义分块那边 `_extract_entities` 是有 `[一-鿿]{2,8}` 的。所以中文查询的 keyword boost 基本空转——这是两个函数提取逻辑不一致导致的。

**Q3.2.8 邻接 chunk 召回干嘛的？**

**答题思路**：一句话——补上下文，防止断章取义。

**参考答案**：
> 语义分块可能把一个完整知识点切在两块里，召回主 chunk 后，我再用它的 `previous_chunk_id` / `next_chunk_id` 把前后文补回来（前 3 条、最多补 5 个，标记 `_adjacent`、score 0.3）。没有它，回答可能只拿到知识点的一半，断章取义。

**Q3.2.9 rerank 挂了整体会怎样？**

**答题思路**：答"跳过 rerank，检索不崩"，别慌。

**参考答案**：
> `_rerank` 超时或非 200 会返回空列表，然后直接跳过 rerank，用 RRF 排序的结果往下走，靠 `score≥0.6` 过滤。所以检索不会崩，只是少了一道精排，精度略降。

### 3.3 意图识别（Router）

**Q3.3.1 真是"规则+LLM 两阶段"吗，confidence 谁给的？**

**答题思路**：⚠️ 规则是死代码 + confidence 硬编码。

**参考答案**：
> 名不副实。规则版 `route_intent_sync` 硬编码返回 `confidence=0.5`，而升级条件是 `<0.8`，所以只要模型可用，**每次都会去调 LLM**，规则那一路只在 LLM 抛异常时兜底。而且 confidence 是硬编码的——LLM 版 0.9、规则版 0.5，模型根本没输出置信度。所以这不是"规则先筛、拿不准再精判"的 cascade。

**Q3.3.2 路由是单轮还是多轮？**

**答题思路**：答"单轮、只看最后一条消息"，再答后果。

**参考答案**：
> 单轮。`_get_last_user_message` 只取最后一条用户消息，不看历史。后果是上下文中的指代（比如用户说"那这个呢"）无法结合上一轮意图判断，容易判偏。

**Q3.3.3 6 场景互斥硬判的局限？**

**答题思路**：答"无多标签、无优先级"。

**参考答案**：
> 6 个场景是互斥的，`_clean_scene` 取第一个命中的场景代码，没有多标签、没有优先级。用户一句话如果同时是"调研"又是"代码"，只会落到其中一个，另一个意图就被丢了。更合理的是允许多标签或给一个置信度排序。

**Q3.3.4 confidence 硬编码的影响？**

**答题思路**：答"拿不到真不确定度，无法低置信度追问"。

**参考答案**：
> 硬编码 0.9/0.5 意味着拿不到模型真实的"不确定度"，就没法做"低置信度时追问确认"这个动作，只能硬塞进 general 或默认模块。正确做法是让模型结构化输出 `scene + confidence + reason`，低于阈值就反过来问用户一句。

### 3.4 Planner 与任务契约

**Q3.4.1 completeness 是代码算的还是 LLM 估的？**

**答题思路**：⚠️ 文档和代码错位的经典题。

**参考答案**：
> 是 LLM 直接输出的。Planner 让模型返回 `is_complete` 和 `completeness`，代码直接读 `plan.get("completeness")`，`is_complete` 驱动路由。那个确定性函数 `calculate_completeness`（维度权重加权）其实**只在 `_generate_fallback_questions` 里被调用**，用于 LLM 没给追问时兜底重算 gaps。所以文档里"维度权重驱动完整度"的说法不准确——真正驱动流程的是 LLM 的估计。

**Q3.4.2 两套权重是同一套还是两套？**

**答题思路**：⚠️ 两套，别混。

**参考答案**：
> 两套，独立存在。一套是维度权重（purpose 0.25、output_style 0.20…），用来拼 dims_desc 注入 prompt、以及 `calculate_completeness` 兜底。另一套是契约 confidence 加权（goal 30% + scope 25% + constraints 15% + …），写在 Planner 的 system prompt 里，让 LLM 估 `contract.confidence`。它们作用在不同环节，一个偏"信息维度完整度"，一个偏"契约整体置信度"。

**Q3.4.3 scope.out 为什么比 in 更重要？**

**答题思路**：负空间定义边界 + 空 out 的惩罚。

**参考答案**：
> scope.out 是"不要做什么"，它定义的是任务的**负空间边界**，防止执行时范围无限膨胀。它比 in 更重要，是因为"做什么"容易说清，但"不做什么"才是防失控的关键。所以我的规则是：scope.out 为空是最大风险信号，contract 的 confidence 至少减 0.2。

**Q3.4.4 JSON 三层降级分别是什么？**

**答题思路**：三次尝试 + 一个故意兜底。

**参考答案**：
> 三层：一是 `json.loads` 直接 parse；二是抠 ```` ```json ```` 代码块再 parse；三是正则 `\{.*\}` 抠第一个 `{...}` 再 parse。全失败还有第 4 层兜底，返回 `{"is_complete": False, "completeness": 0.3, ...}`——故意让 `is_complete=False`，把流程推向"追问用户"，而不是直接崩溃。

**Q3.4.5 `_fallback_plan` 什么时候触发，用什么判断完整度？**

**答题思路**：⚠️ 区分"LLM 抛异常"和"JSON 解析失败"。

**参考答案**：
> 只在 **LLM 调用抛异常**时触发（比如网络错、模型挂了），不是"JSON 解析失败"——那走的是 `_parse_planner_json` 的第 4 层兜底。`_fallback_plan` 用**消息长度**当完整度代理：<20 字判不完整、追问"详细说说"；20~100 字判半完整、追问"具体要求"；≥100 字判完整、直接执行。因为 LLM 挂了，代码手里只剩消息长度这个最便宜的信号。

**Q3.4.6 多轮维度怎么合并，什么条件覆盖？**

**答题思路**：保守合并——置信度更高才覆盖。

**参考答案**：
> `_merge_dimensions_from_plan` 里，新提取的维度只有在**置信度高于旧值**时才覆盖，否则保留旧值。这是保守策略，防止低置信度的新提取冲掉已经确认的信息。

### 3.5 ReAct / 工具

**Q3.5.1 skill 和 tool 什么关系？**

**答题思路**：skill = 人设 + 工具白名单；tool = 单个函数；多对多。

**参考答案**：
> tool 是一个 `@tool` 装饰的、LLM 能调用的单个函数，比如 `search_knowledge_base`。skill 是一个能力模块，等于「专属 System Prompt（人设）+ 工具白名单」。对应关系靠两个表：`_SKILL_SYSTEM_PROMPTS` 管人设，`SKILL_TOOL_MAP` 管工具子集。是多对多——4 个 skill 共享 4 个工具（search/add_to_kb/save_memory/export_md），另外 3 个工具（python_exec/run_shell/write_file）故意不给任何 skill。

**Q3.5.2 execute 里 ReAct 建了几次？skill 的 execute() 什么时候被调？**

**答题思路**：⚠️ 建两次 + skill 死代码。

**参考答案**：
> 建了两次，而且是冗余的。`execute_node` 直接用 `create_react_agent(model, tools, prompt)` 建一次（主路径）；skill 类自己的 `execute()` 方法内部又建一次。而 `skill_instance.execute()` 只在**主路径 ReAct 没产出任何文本**时才被 `_execute_legacy_skill` 调用兜底。所以 skill 实例的 `execute()` 大部分时候是死代码，真正在用的是 skill 的 System Prompt 和工具白名单。

**Q3.5.3 bind_tools 和 create_react_agent 各自干什么？**

**答题思路**：一个挂 schema，一个编译循环。

**参考答案**：
> `bind_tools(tools, parallel_tool_calls=True)` 是把工具 schema 挂到模型上，告诉它"你能调这些函数"，`parallel_tool_calls=True` 允许一轮同时发多个 tool call。`create_react_agent` 是用这个绑好工具的模型编译一个循环图：LLM 推理 → 调工具 → 看结果 → 再推理，直到输出纯文本或到轮数上限。

**Q3.5.4 3 个工具为什么不分配给 skill？**

**答题思路**：定位问题，不是能力问题。

**参考答案**：
> 是定位问题。阿福的定位是"协作引导者"而非"执行者"，所以 `python_exec`（跑代码）、`run_shell_preview`（跑 shell）、`write_file`（写文件）这三个"动手"工具故意不暴露给任何 skill，避免它越界替用户干不可逆的活。

**Q3.5.5 ReAct 循环有轮数上限吗？**

**答题思路**：⚠️ 配置写了但没接上。

**参考答案**：
> 配置层有 `max_tool_rounds=10`，但 `execute_node` 创建 `create_react_agent` 时**没有传这个值，也没传 `recursion_limit`**。所以实际兜底是 LangGraph `create_react_agent` 的默认 recursion limit，而不是我以为的 10 轮。文档里描述的 loop_guard 防打转机制是设计稿，没有在 execute 落地。这是我后来发现的"配置和代码脱节"点。

**Q3.5.6 子图 token 能冒泡到外层 astream_events 吗？**

**答题思路**：⚠️ LangGraph 架构限制。

**参考答案**：
> 不能。`create_react_agent` 是一个**子图**，它的 token 事件不会冒泡到外层图的 `astream_events`——这是 LangGraph 的设计。所以 execute 节点内部只能做**节点级**流式（推"执行中…"这类进度），不是 token 级。这个坑我当时是 debug token 统计发现 execute 的 token 是 0 才定位到的。

### 3.6 工程规范顾问

**Q3.6.1 三级输出模式，分级依据？**

**答题思路**：建议/确认/阻断，依据是风险不是重要程度。

**参考答案**：
> 三级是：建议（suggestion，注入上下文不打断）、确认（confirm，暂停问用户）、阻断（block，硬停）。分级依据是**风险等级**，不是重要程度——风险越高越往上走，从"默默提一句"到"停下来问"再到"直接叫停"。

**Q3.6.2 "降级匹配"为什么叫降级？现在是唯一路径吗？**

**答题思路**：⚠️ RAG 主路径没接上。

**参考答案**：
> 它本意是"RAG 检索知识卡片"的降级方案，但 RAG 那部分注释写着"待 chunk_type 索引完善后再接入"，**根本没接上**。所以现在 `_fallback_match`（用内置的硬编码触发器 dict）其实是唯一在跑的实现——名字叫"降级"，实际是唯一路径。

**Q3.6.3 命中多场景时 mode 怎么定？**

**答题思路**：取最高等级。

**参考答案**：
> 取所有命中场景里的**最高等级**。按 level 降序排，`max_level≥3` 就 block、`≥2` 就 confirm、否则 suggestion。木桶最高板，不是平均——只要有一条阻断级风险就整段阻断。

### 3.7 流式输出

**Q3.7.1 节点级还是 token 级，为什么 execute 的 token 看不到？**

**答题思路**：节点级 + 子图不冒泡。

**参考答案**：
> 节点级。因为 execute 内部 `create_react_agent` 是子图，token 不冒泡（见 3.5.6），所以执行节点只能推节点进度事件，不是逐 token。

**Q3.7.2 断连怎么处理？**

**答题思路**：⚠️ 当前没做显式检测。

**参考答案**：
> 目前代码里没有显式的 `is_disconnected` 检测。SSE 用 sse-starlette，客户端断连后一般由框架收尾，后台 graph 大概率继续跑完，浪费算力。这是可改进点——理想是检测到断连就取消后台任务。

### 3.8 可靠性与测试

**Q3.8.1 测试策略和 CRUD 项目最根本的区别？**

**答题思路**：非确定性 → 测确定性、监控非确定性。

**参考答案**：
> 最根本区别是 LLM 输出非确定——同一输入每次结果可能不同，传统"输入 A 断言输出 B"不成立。所以我的策略是"测确定性部分、监控非确定性部分"：维度合并、完整度计算、JSON 解析、降级逻辑这些确定性的用单测覆盖；语义漂移、幻觉这些非确定性的靠 checkpoint/reflect 质检节点 + 人工监控兜底。

**Q3.8.2 25 个测试覆盖什么，故意不测什么？**

**答题思路**：21 + 5，故意不测生成内容正确性。

**参考答案**：
> 21 个在 `test_graph.py`，测维度合并、完整度计算、追问生成、JSON 解析、降级逻辑；5 个在 `test_session_store.py`，测 Session CRUD、消息读写、级联删除、反馈统计。故意不测的是 LLM 生成内容的"正确性"——这个不可测，靠质检节点和人工监控。

### 3.9 综合连环问

**Q3.9.1 "帮我做论坛"完整走一遍，哪里最可能出问题？**

**答题思路**：完整链路 + 指一个具体风险点。

**参考答案**：
> router 判成 work_plan → enrich 透传 → rag 注入论坛相关知识 → planner 提取维度（技术栈？功能范围？时间？）判断不完整 → clarify 追问 → engineering_check 可能因"数据库/部署"触发确认 → execute 的 ReAct 调 search_knowledge_base 查技术选型 → checkpoint 查语义对齐 → reflect 查质量。最可能出问题的是两处：planner 维度提取不全（论坛功能边界太模糊），以及 execute 的 ReAct 可能跑偏成"写一份如何开发论坛的规划文档"而不是实际执行——这是我记录过的语义漂移问题。

**Q3.9.2 embedding 整体挂了，完整降级链怎么串？**

**答题思路**：逐环节说"降级不崩溃"。

**参考答案**：
> RAG 的 dense 检索失败会走 `query` 的 except 兜底或降级 legacy collection，最后返回"未找到知识"的话术；L3 事实提取降级到正则规则、召回降级到内存关键词；UserProfile/SessionMemory 的写入失败只记日志不阻断主流程。整体原则是**降级不崩溃**——每个依赖外部 embedding 的环节都有本地兜底，最坏情况就是"没有知识库参考、基于通用知识回答"。

**Q3.9.3 是不是过度设计，哪个可砍？**

**答题思路**：开放，但有自我审视。点一个真实冗余。

**参考答案**：
> 确实有过度设计的成分。最该砍的是记忆系统的冗余——我现在有 ContextEngine 的 L3 事实、SessionMemory 的摘要、UserProfile 的画像三套东西，都在记"用户偏好"，功能重叠且没有形成"事实→摘要→画像"的递进链，同一段对话被 LLM 重复抽取。理想是合并成一条递进链。另外知识图谱（Source→Document→Chunk→Claim）目前主要是元数据冗余，Claim 层基本没被消费，也可以砍。

**Q3.9.4 砍掉一半复杂度砍哪一半？**

**答题思路**：同上，但要具体到"砍了会失去什么、为什么能接受"。

**参考答案**：
> 我会先砍多 Agent Panel 和知识图谱的 Claim 层。前者只在"明确要求对比"时才触发，频次低，收益可以用"一个 LLM 分三段输出"近似；后者 Claim 存了但没检索路径消费它，纯冗余。这样能省掉一条并行节点和一张表，复杂度降下来，而核心的"引导式对话 + 混合检索 + 三层上下文"不受影响。

**Q3.9.5 最薄弱、最不愿被问到的点？**

**答题思路**：诚实 + 有代码依据。任选一个真实弱点。

**参考答案**：
> 最薄弱的是检索的稀疏通道——它没索引（GIN 建错字段导致全表扫描），数据量一大就会成为瓶颈，而且"BM25"这个说法不准确。我一直知道但没来得及修，因为它现在数据量小、不暴露。如果面试被问性能，这是我第一个想藏起来的点，但也是最能体现"我知道自己系统弱点在哪"的点。

## 阶段 4：系统设计与场景题

**Q4.1 100 用户并发，哪里先出问题？**

**答题思路**：按"内存 / 连接 / 连接数 / 外部 API"四点答，各配一个改法。

**参考答案**：
> 先炸的是这几处：一是 ContextEngine 的内存字典是单进程 `dict`，多实例部署时不共享、并发下有锁竞争，要换 Redis；二是 PGVector 是懒加载单连接、非连接池，并发请求会排队，要换连接池或异步驱动；三是 SSE 长连接占满 worker；四是 embedding/rerank 走外部 API 没有并发限流。对应改法：内存上 Redis、DB 上连接池、SSE 加连接上限、外部 API 加限流重试。

**Q4.2 知识库涨到 20 万 md，哪里先瓶颈？**

**答题思路**：稀疏无索引 → 最先炸，然后 embedding 全量重算。

**参考答案**：
> 最先炸的是稀疏检索——它现在没索引、全表扫描，20 万条必挂。要给 `search_text_sparse` 建 GIN 或物化 tsvector 列。其次是 embedding 全量重算，要改增量索引 + 批量；rerank 虽然只对 top-20，但粗排召回 20 万级需要调 IVF/HNSW 参数，且粗排候选数要动态调整。

**Q4.3 新会话引用上周决策，怎么做？**

**答题思路**：现状 + 要改的方向。

**参考答案**：
> 现状是 L3 检索按 session_id 过滤（会话隔离），跨会话靠 SessionMemory，但只有新会话首条消息带"继续/上次"这类信号才触发检索。要引用上周决策，方向是：给 L3 加跨会话兜底，或引入"关联会话/项目"的显式概念，让记忆能按"项目"而不是按"会话"聚合。

**Q4.4 1M 窗口下，三层上下文 + RAG 会不会浪费？**

**答题思路**：窗口大≠该全塞，核心是"取舍和压缩"。

**参考答案**：
> 不会浪费，反而更必要。1M 窗口大不代表该全塞——噪音会稀释注意力、还烧 token。三层上下文的本质是"对窗口内容做取舍和压缩"：该全塞的时候（短对话、强上下文依赖）全塞，该检索的时候（长文档、海量知识）走 RAG。窗口越大，越需要一套机制去决定"塞什么、不塞什么"。

**Q4.5 加定时任务/主动推送，冲突在哪？**

**答题思路**：无状态请求-响应 vs 常驻推送。

**参考答案**：
> 冲突在：现在是无状态的请求-响应模型，每次请求起一次 graph、SSE 推一次流。要加主动推送，需要常驻进程 + 任务队列（Celery/APScheduler）+ WebSocket 或服务器推送，把"拉"改成"推"。现状架构（FastAPI + 每次请求起 graph）不支持主动触达，得加一层调度和推送通道。

## 阶段 5：反问

略——那是你问面试官的，没有标准答案。核心：问"团队怎么做评测/可观测性/幻觉治理"，比问"加班吗"显水平。
