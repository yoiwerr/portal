# Alfred 产品定义

确认日期：2026-10-09。本文是当前产品范围与交付标准的依据；旧能力规范、任务契约教程和历史开发记录与本文冲突时，以本文为准。

本文描述已确认的目标设计。现有代码尚未全部对齐，实施进度与验收见 [逐步优化路线](docs/product-roadmap.md)。

## 定位与用户

Alfred 是面向新手的 Vibe Coding 项目方案助手。

用户通常只有一个想法，可能从未开发过软件，也不知道框架、数据库、部署等术语的含义。Alfred 帮他们拆解想法、理解选择、限定第一版范围，最终得到一份可以直接交给 Codex 等编程 Agent 开始实施的方案文案。

Alfred 负责形成方案。编程 Agent 负责生成代码、实际诊断错误、运行测试和部署。产品首版只支持从零开始的新项目。

## 成功体验

用户不用先补一门开发课程，也不用凭感觉选一堆技术名词。聊完后，他能说清「要做什么、先做哪些、怎么判断做完了」，并把一个完整文档交给编程 Agent。

交付不是聊天记录摘要，也不是只有几百字的任务卡。用户和 Agent 使用同一份方案：主要内容用日常语言说明，实施所需的技术名称及约束在相关位置写清楚。

## 对话规则

1. 从实际使用场景提问：谁使用、要完成什么、一次完整操作怎么走、结果留在哪里。
2. 优先澄清会改变核心行为和第一版范围的问题，避免让用户填写技术问卷。
3. 必须用到术语时先解释实际作用，再给名称。一次围绕一个决策讲清体验、费用和维护影响。
4. 给出案例、优缺点和推荐，不把用户不理解的选项当成已完成的决策。
5. 用户说「不懂」「随便」「按你的建议」时，采用默认方案并说明理由，不用同一个问题反复卡住流程。
6. 对矛盾、遗漏、过大范围主动提醒；提出删减或分期建议，说明影响。改变用户核心要求前需要确认。
7. 信息足够后生成方案，不以固定轮数、所有字段都由用户手动回答为结束条件。

例如，用户说「我想记录读过的书」时，先问「只有你自己用，还是想让朋友也有自己的书单？」；需要解释部署时，可以说「只在自己电脑打开最省事；想用手机随时访问，就需要一个持续运行的地方，会有服务器或托管费用」。

## 默认兜底

默认值是底层兜底：没有明确需求或偏好时，选择能实现核心目标的最简单、小规模方案。

| 决策 | 缺少偏好时的原则 |
| --- | --- |
| 用户与规模 | 以个人或小规模使用为假设，不主动设计高并发、全球多区域 |
| 第一版 | 先完成核心流程，扩展功能单列后续，不偷偷删掉用户明确要求 |
| 架构 | 优先少组件、单体或单个部署单元；没有实际需要不引入微服务、队列或集群 |
| 技术选择 | 使用成熟、常见、容易交给 Agent 实施和维护的组合；具体栈随后整理成可评估的默认方案 |
| 数据 | 需要保存的数据必须持久化；根据实际需要说明备份与恢复 |
| 权限 | 按使用场景定义访问规则，不把公开访问或弱密码当成简化方案 |
| 部署 | 给出满足访问需求的最简单路径，区分本地试用与持续运行 |
| 费用 | 说明免费条件、收费来源和预算假设，不承诺未知服务永久免费 |

默认不能覆盖明确要求、安全底线或数据可靠性。预算、人数等未提供的内容标为假设，不能捏造为用户已确认的事实。默认小规模方案不意味着把 Alfred 自身的 PostgreSQL 等工程配置改成另一套技术栈。

当前只确认默认原则，尚未确定统一的框架、托管平台或具体预算数字。后续优化需要整理少量适用场景与默认组合，不建立庞大的技术选型问卷。

## 何时交付

同时满足以下条件，可以生成最终方案：

- 核心目标和目标用户清楚。
- 主要场景与完整使用流程可以描述。
- 第一版范围和明确排除项清楚，关键矛盾已解决。
- 有可观察的验收标准。
- 其余实施细节已有明确要求，或能用标注清楚的默认方案补齐。

若不确定项会改变核心功能、权限、不可接受的费用或数据处理方式，不能默默猜测，需继续澄清。非阻塞的后续增强可以列在「待定事项」，不能把决定第一版能否实施的问题留给 Agent 猜。

## 唯一最终交付物：项目实施方案

交付一份独立文案，推荐采用 Markdown，能复制或导出。不能依赖隐藏记忆、旧聊天或另一个交接卡才能实施。

按项目实际需要覆盖：

1. **目标与场景**：解决什么问题，谁使用，一次完整使用的例子。
2. **第一版范围**：必做功能、明确不做、后续阶段；保留用户明确要求。
3. **页面与流程**：主要入口、操作、状态反馈、空状态及必要的失败处理。
4. **技术与架构建议**：具体推荐、普通语言解释、适用规模、成本和维护取舍。
5. **数据与权限**：保存什么、归属谁、谁可查看或修改、必要的业务规则。
6. **实施任务**：有依赖顺序的阶段，每阶段的交付和验证方式。
7. **部署与运行**：本地试用、正式部署、配置项用途、安全、备份恢复及费用假设。
8. **验收标准**：能通过操作、测试或检查观察到的结果，避免只写「正常」「体验好」。
9. **错误处理方案**：要求编程 Agent 收集复现步骤、错误输出和环境，定位、修复并回归验证；敏感信息脱敏、风险操作先确认。
10. **决策来源**：分别列出已确认要求、Alfred 推荐的默认假设和非阻塞待定事项。

文案可以指明技术、数据结构含义、接口行为和配置项用途，但不附代码、伪代码、SQL、可执行配置或命令脚本。实现细节由编程 Agent 按方案生成。这里的限制约束 Alfred 的产品输出，不限制开发者维护本仓库时使用代码与命令。

交付前检查：没有相互矛盾的要求；核心路径可以端到端实施；关键数据和权限明确；默认假设可识别；阶段任务可验证；用户无需理解未解释的术语；Agent 无需重新猜测核心需求。

## 范围与边界

首版包含需求拆解、技术方案解释、默认推荐、范围取舍、任务分期、部署安全备份成本规划和最终方案文案。

首版不包含：

- 编写或审查项目代码、输出可执行文件、直接修改项目。
- 执行命令、接管编程 Agent、代替用户部署。
- 接手真实报错的诊断与修复；只能提供排错工作的处理方案。
- 现有项目改造；这需要另行建立输入、现状分析和变更流程。

检索、内部规划和质量检查等实现机制可以服务于方案生成，但不能因此扩大为用户项目的执行工具。

## 暂缓的产品决策

后续修改方案有价值，但采用「记住项目后继续聊」还是「用户带着上次方案来修改」尚待调研。现有记忆代码和会话持久化不代表该产品决策已经确认；保存当前对话与承诺跨会话自动恢复项目是不同问题。

已有项目改造、持续项目跟进也不纳入首版承诺。先验证新项目的澄清、默认与单文档交付，再设计独立流程。

## 视觉与交互原则

保留沉稳、克制、可靠的气质，内容前置，不卖弄技术。中文为主要界面语言，深色主题为当前默认，金色仅作少量状态、选中态及主操作点缀。

现有三栏工作台（左契约、中对话、右索引）是实现现状；后续围绕想法、对话和方案安排信息，不要求新手先理解「任务契约」。本次文档调整不重做界面。

- 长对话优先，分区清楚，各区滚动互不干扰。
- 避免赛博朋克、霓虹发光、夸张渐变、奶油色 SaaS 背景、海报式大标题、装饰性玻璃卡片和多彩图表。
- 以 WCAG AA 为目标，尊重 `prefers-reduced-motion`。
- 默认假设与待定事项必须可读，不用颜色作为唯一识别方式。
