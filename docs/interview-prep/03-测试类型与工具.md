# 03 · 测试类型与工具

---

## 一、测试类型全景 ⭐⭐

### 1. 功能测试

> 验证软件是否**按需求做对了事**。

- **核心**：对照需求文档，逐条验证功能是否正确实现
- **手段**：手工为主，自动化辅助
- **重点**：不只看"能不能用"，还要看"好不好用"

**面试话术**：
> 功能测试是我日常最主要的工作。我会先理解需求，然后用等价类、边界值、场景法设计用例，执行后记录结果。不仅是验证"能跑通"，还包括异常情况、边界条件、用户可能误操作的场景。

---

### 2. 回归测试

> 验证**改动没有破坏原有功能**。

**策略（面试要能讲）**：

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| 全量回归 | 所有用例重新跑一遍 | 大版本、架构变更 |
| 选择性回归 | 只跑受影响模块+核心流程 | 小 Bug 修复 |
| 自动化回归 | 用脚本跑核心用例 | 高频迭代 |

**实战经验话术**：
> 在实际项目中，每次发版前我们都会做一轮回归。小改动就回归关联模块+核心业务流程；大版本就全量回归。我会优先把核心流程写成自动化脚本，节省手工回归的时间。

---

### 3. 兼容性测试

> 验证软件在**不同环境**下能否正常工作。

**兼容性维度**：

| 维度 | 测试内容 |
|------|----------|
| 浏览器 | Chrome / Edge / Safari / Firefox（不同版本） |
| 操作系统 | Windows / macOS / iOS / Android |
| 分辨率 | 1920×1080 / 1366×768 / 移动端 |
| 网络 | WiFi / 4G / 5G / 弱网 |

**实战策略**：不可能全覆盖 → 根据用户画像选择**主流组合**
- 例如：内部管理系统 → 只测 Chrome 最新版
- 例如：面向消费者的 H5 → Chrome + Safari + 主流手机型号

---

### 4. 接口测试（API 测试）⭐

> 绕过前端界面，**直接测试后端接口**。

**为什么重要**：
- 前端还没开发完，后端接口可以先测
- 很多 Bug 其实在前端看不到，是接口层的问题
- 自动化比 UI 自动化稳定得多

**用 Postman 做接口测试（重点掌握）**：

```
典型测试步骤：
1. 创建 Collection（如"用户模块"）
2. 添加 Request：
   - Method：GET / POST / PUT / DELETE
   - URL：http://test-api.example.com/api/v1/users
   - Headers：Content-Type: application/json, Authorization: Bearer xxx
   - Body（POST/PUT）：JSON 格式的请求体
3. 发送请求 → 检查 Response：
   - Status Code：200 / 201 / 400 / 401 / 500
   - Response Body：字段名、类型、值是否正确
   - Response Time：是否在合理范围内
4. 写 Tests 脚本（Postman 支持 JS）：
   pm.test("状态码是 200", () => pm.response.to.have.status(200));
   pm.test("返回包含 token", () => pm.expect(pm.response.json().data).to.have.property("token"));
```

**接口测试测什么**：

| 测试点 | 说明 | 示例 |
|--------|------|------|
| 正常请求 | 正确参数 → 正确返回 | 正确的用户名密码 → 返回 token |
| 必填参数 | 缺少必填 → 返回错误码+提示 | 不发手机号 → 400 + "手机号必填" |
| 参数类型 | 类型不对 → 返回错误 | 年龄传 "abc" → 400 |
| 参数范围 | 边界值 → 正确处理 | 页码传 0 或 -1 → 返回空或报错 |
| 鉴权 | 无 token / 过期 token → 401 | 不带 Authorization → 401 |
| 异常数据 | SQL 注入 / XSS → 被过滤 | 用户名传 `<script>alert(1)</script>` |

### 5. 自动化测试基础

**金字塔模型（面试要能画）**：

```
        /\
       /UI\          ← UI 自动化：少量，成本高、维护难
      /────\
     / 接口 \        ← 接口自动化：中等量，ROI 最高
    /────────\
   /  单元测试 \     ← 单元测试：最多，运行快、定位准
  /────────────\
```

**入门建议话术**：
> 我目前主要做手工测试，但会写简单的接口自动化脚本。比如用 Postman Collection Runner 批量跑接口用例，或者用 Python + requests 写一些回归用的接口脚本。我理解自动化不是替代手工测试，而是把重复的、高频的验证交给机器，手工测试专注于探索性和复杂场景。

## 二、测试工具速查 ⭐⭐

### 1. Jira — 缺陷/用例管理

```
Jira 中一个 Bug 的标准操作流程：
1. Create Issue → 类型选 "Bug"
2. 填写 Summary（标题）、Description（描述）、Steps to Reproduce
3. 设置 Priority（优先级）、Severity（严重程度）、Affects Version
4. Assign 给对应的开发
5. 开发修复后 → 状态变为 Resolved
6. 测试验证 → Close 或 Reopen

常用 JQL 查询（加分项）：
  - project = PROJ AND issuetype = Bug AND status = Open   → 查看所有待处理 Bug
  - assignee = currentUser() AND status != Closed          → 我负责的未关闭问题
  - created >= -7d AND priority = Highest                  → 最近一周的紧急问题
```

### 2. Notion — 用例/文档管理

```
Notion 做测试管理：
  - Database 建"测试用例库"，字段：模块/标题/步骤/预期/优先级/状态
  - 按模块分组视图（Board View）
  - 按执行状态过滤（Table View + Filter）
  - 测试报告写在 Notion Page 中，嵌入用例执行统计
```

### 3. Postman — 接口测试

> 详见上方接口测试部分

**常用技巧**：
- **环境变量**：`{{base_url}}` 切换测试/生产环境
- **Pre-request Script**：自动生成签名、获取 token
- **Collection Runner**：批量执行用例
- **Newman**：命令行跑 Postman Collection，可集成到 CI/CD

### 4. Charles / Fiddler — 抓包工具

> 拦截 HTTP/HTTPS 请求，查看和修改请求/响应内容。

**典型使用场景**：

| 场景 | 操作 |
|------|------|
| 前端显示不对，看是不是接口返回的数据就错了 | 抓包看 Response |
| 想测试前端对异常数据的处理 | 断点修改 Response，返回异常数据 |
| 弱网测试 | 限速（Throttle），模拟 2G/3G |
| 定位问题是前端还是后端 | 抓包：接口返回正确→前端问题；返回错误→后端问题 |
| 查看 App 实际请求了哪些接口 | 手机设代理到 Charles |

**常用操作**：
- **筛选**：`Filter` 只显示目标域名
- **断点**：`Breakpoints` → 拦截并修改请求/响应
- **限速**：`Throttle Settings` → 模拟弱网
- **HTTPS 抓包**：安装 Charles 证书 → SSL Proxying 开启

## 三、SQL 基础 ⭐⭐

> 测试工程师不需要写复杂 SQL，但**单表查询 + 多表联查**是必备技能。

### 常用场景

| 场景 | SQL |
|------|-----|
| 验证注册是否写入数据库 | `SELECT * FROM users WHERE phone = '138xxxx';` |
| 查看订单状态 | `SELECT id, status, amount FROM orders WHERE user_id = 123;` |
| 造测试数据 | `INSERT INTO users (name, phone) VALUES ('测试用户', '13800000000');` |
| 清理测试数据 | `DELETE FROM users WHERE phone LIKE '138%测试%';` |
| 修改订单状态（模拟场景） | `UPDATE orders SET status = 'paid' WHERE id = 456;` |

### 必会语法清单

```sql
-- 基础查询
SELECT 字段1, 字段2 FROM 表名
WHERE 条件 AND 条件2
ORDER BY 字段 DESC
LIMIT 10;

-- 聚合
SELECT COUNT(*), SUM(amount), AVG(amount)
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY user_id;

-- 多表联查
SELECT u.name, o.id, o.amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.id = 123;

-- 子查询
SELECT * FROM orders
WHERE user_id IN (
  SELECT id FROM users WHERE vip_level = 3
);
```

### 面试常见 SQL 题

**Q1：查询每个用户的订单数量**
```sql
SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id
ORDER BY order_count DESC;
```

**Q2：查询昨天注册但还没下过单的用户**
```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.created_at >= DATE('now', '-1 day')
  AND o.id IS NULL;
```

**Q3：找出重复的手机号**
```sql
SELECT phone, COUNT(*) AS cnt
FROM users
GROUP BY phone
HAVING cnt > 1;
```
