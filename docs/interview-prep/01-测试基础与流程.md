# 01 · 测试基础与流程

---

## 一、什么是软件测试 ⭐

> 软件测试是通过**手工或自动化手段**运行或评估软件系统的过程，目的是**发现缺陷**、**验证软件是否满足需求**、**评估软件质量**。

**核心认知（面试要说的）：**

| 常见误解 | 正确认知 |
|----------|----------|
| 测试是找 bug | 测试是**质量信息的提供者**——我们告诉团队产品现在是什么状态 |
| 测试在开发之后 | 测试活动从**需求阶段**就应该介入 |
| 测试保证质量 | 测试**不能保证**质量，只能**评估和报告**质量 |
| 测试完了就没 bug 了 | 测试只能证明**存在缺陷**，不能证明**没有缺陷** |

---

## 二、软件测试流程 ⭐⭐⭐

```
需求分析 → 测试计划 → 测试设计 → 测试执行 → 缺陷跟踪 → 测试报告 → 版本准出
```

### 阶段详解（面试要用自己的话讲一遍）

#### 1. 需求分析
- **做什么**：阅读 PRD/需求文档，理解业务逻辑，识别模糊点
- **输出**：需求疑问列表、测试关注点
- **关键动作**：参加需求评审会，**在开发写代码之前就质疑不合理的设计**

#### 2. 测试计划
- **做什么**：确定测试范围、测试策略、资源分配、时间安排
- **输出**：测试计划文档
- **关键内容**：哪些要测 / 哪些不测（为什么）、谁来测、什么时候测完

#### 3. 测试设计
- **做什么**：编写测试用例，准备测试数据
- **输出**：测试用例集、测试数据
- **方法**：等价类、边界值、场景法、判定表（→ 详见 02 文档）

#### 4. 测试执行
- **做什么**：按用例执行测试，记录结果
- **关键**：先做**冒烟测试**，通过了才进入全面测试
- **产出**：执行记录、发现的 Bug 列表

#### 5. 缺陷跟踪
- **做什么**：提交 Bug、跟进修复、回归验证、关闭
- **关键**：每个 Bug 都要有**闭环**——提交→确认→修复→验证→关闭

#### 6. 测试报告
- **做什么**：总结本轮测试，给出质量评估
- **关键数据**：用例通过率、Bug 收敛趋势、遗留问题

#### 7. 版本准出
- **做什么**：判断版本是否可以发布
- **准出条件**（典型）：
  - 用例执行率 100%
  - 致命/严重 Bug 清零
  - 一般 Bug 修复率 ≥ 95%
  - 回归测试通过

## 三、V 模型 vs W 模型（理解即可，被问到能画图）

### V 模型

```
需求分析 ←——————→ 验收测试
   ↓                  ↑
概要设计 ←——————→ 系统测试
   ↓                  ↑
详细设计 ←——————→ 集成测试
   ↓                  ↑
   编码 ←——————→ 单元测试
```

**要点**：左边是开发活动，右边是对应的测试活动。测试不是在编码后才开始的——**每个阶段都有对应的测试活动**。

### W 模型（V 模型的改进）

```
需求分析 → 概要设计 → 详细设计 → 编码
   ↓          ↓          ↓         ↓
需求评审   设计评审   详细设计评审  单元测试
             ↑          ↑         ↑
          系统测试   集成测试      ↓
```

**要点**：测试活动**更早介入**（需求阶段就开始评审），测试和开发**并行**进行。

## 四、关键概念字典 ⭐⭐

### 冒烟测试 (Smoke Testing)

> 在新版本上进行**最基础的功能验证**，确认系统的主要功能可用，没有"冒烟"。

- **时机**：拿到新版本后**第一件事**
- **范围**：核心功能，用例数少（通常 10-30 条）
- **结果**：通过 → 进入全面测试；不通过 → 打回开发
- **类比**：买手机开箱，先按开机键——能亮再继续看细节，不能亮直接退货

### 回归测试 (Regression Testing)

> 验证**修改代码后，原有功能是否仍然正常**。

- **时机**：Bug 修复后、版本迭代后、代码合并后
- **范围**：被修改模块 + 关联模块 + 核心业务流程
- **为什么重要**：开发修一个 Bug 可能引入三个新 Bug
- **策略**：全量回归（大版本）vs 选择性回归（小修改）

### 准出标准 (Release Criteria / Exit Criteria)

| 维度 | 典型标准 |
|------|----------|
| 用例执行 | 执行率 = 100%，通过率 ≥ 95% |
| 缺陷 | P0/P1（致命/严重）Bug = 0，P2（一般）修复率 ≥ 95% |
| 回归 | 回归测试通过 |
| 兼容性 | 目标平台/浏览器验证通过 |
| 文档 | 测试报告已完成 |

### 测试用例 (Test Case)

> 一组测试输入、执行条件、预期结果，为特定测试目标而开发。

```
标准用例包含 8 要素：
1. 用例编号    5. 前置条件
2. 测试模块    6. 测试步骤
3. 用例标题    7. 预期结果
4. 优先级      8. 实际结果
```

## 五、测试优先级划分

| 级别 | 名称 | 说明 | 示例 |
|------|------|------|------|
| P0 | 最高 | 核心功能，阻塞发版 | 登录、支付、数据丢失 |
| P1 | 高 | 主要功能，严重影响用户 | 核心业务流程中断 |
| P2 | 中 | 次要功能，有替代方案 | 非关键页面报错 |
| P3 | 低 | 边缘场景、体验问题 | UI 文案错别字 |
