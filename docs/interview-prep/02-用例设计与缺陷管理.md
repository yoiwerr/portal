# 02 · 用例设计与缺陷管理

---

## 一、测试用例设计方法 ⭐⭐⭐

> 这是面试的**核心考点**——面试官大概率会让你现场设计用例。

### 1. 等价类划分法

**核心思想**：输入数据可以分成若干"等价类"，每个等价类中的数据对程序的影响相同，**每个等价类只需取一个代表值测试**。

**分类**：
- **有效等价类**：合法的、有意义的输入
- **无效等价类**：非法的、无意义的输入

**经典例题**：一个输入框要求输入 **1-100 的整数**

```
有效等价类：
  ✅ [1, 100] 之间的整数 → 取 50

无效等价类：
  ❌ 小于 1 → 取 0 或 -5
  ❌ 大于 100 → 取 101 或 200
  ❌ 小数 → 取 3.14
  ❌ 非数字 → 取 "abc"
  ❌ 为空 → 不填
  ❌ 空格 → "   "
  ❌ 特殊字符 → "@#$"
```

**面试话术**：「等价类划分的目的是用最少的用例覆盖最多的场景。我会先识别输入域，然后分成有效和无效等价类，每个类取一个代表值。」

---

### 2. 边界值分析法 ⭐

**核心思想**：Bug 往往藏在边界上，所以要重点测边界值。

**取点规则**：边界值取 **边界点 ±1**

```
输入范围 [1, 100] 的边界值测试：

  min-1 = 0    (边界外)
  min   = 1    (边界上)
  min+1 = 2    (边界内)
  max-1 = 99   (边界内)
  max   = 100  (边界上)
  max+1 = 101  (边界外)

  再加上正常值 50 → 共 7 个用例
```

**面试话术**：「等价类和边界值通常是组合使用的——先用等价类划分找到测试范围，再用边界值确定具体取什么数据。边界值是发现 Bug 效率最高的方法。」

**常见边界场景**：
- 数值范围（年龄 0-150）
- 字符串长度（昵称 2-20 字符）
- 列表数量（购物车最多 99 件）
- 时间范围（优惠券有效期）

---

### 3. 场景法 ⭐

**核心思想**：模拟用户实际操作流程，覆盖**基本流 + 备选流**。

**经典例题**：ATM 取款

```
基本流（Happy Path）：
  插卡 → 输入密码 → 选择取款 → 输入金额 → 取钞 → 退卡

备选流（异常/分支）：
  - 密码错误 → 重新输入 → 3 次锁卡
  - 余额不足 → 提示并返回
  - 输入金额不是 100 的倍数 → 提示重新输入
  - 取款中途取消 → 退卡
  - ATM 没钱了 → 提示并退卡
  - 超时未操作 → 吞卡
```

**设计方法**：
1. 画出业务流程图
2. 确定基本流（1 条）
3. 确定备选流（N 条）
4. 组合基本流 + 各备选流 → 形成场景用例

---

### 4. 判定表法

**核心思想**：当输入条件有多个且相互组合时，用表格列出所有条件组合和对应的预期结果。

**经典例题**：「如果用户是会员且订单金额 ≥ 100，免运费；否则收 10 元运费」

| 条件/动作 | 1 | 2 | 3 | 4 |
|-----------|---|---|---|---|
| **条件** |   |   |   |   |
| 是会员？   | Y | Y | N | N |
| 金额 ≥ 100 | Y | N | Y | N |
| **动作** |   |   |   |   |
| 免运费     | ✓ |   |   |   |
| 收 10 元   |   | ✓ | ✓ | ✓ |

→ 4 条用例覆盖所有组合

**适用场景**：条件组合多、规则明确的场景（优惠券、权限判断、报销规则）

---

### 5. 正交表法

**核心思想**：当组合太多，用**正交表**从中挑选代表性组合，减少用例量。

- 适用于：多因素多水平的组合，全排列工作量太大
- 工具：可以用正交表生成器或 AI 辅助生成

---

### 6. 错误推测法

**核心思想**：基于经验和对系统的了解，猜测哪里可能出错。

**常见猜测方向**：
- 用户可能做的"反直觉"操作
- 网络异常、超时
- 并发操作
- 数据为空或异常数据
- 上一个 Bug 修复引入的新问题

---

### 实战：综合用例设计示范

**需求**：注册页面，用户名 3-20 字符（字母数字下划线），密码 6-16 位（必须含字母和数字），手机号必填。

```
等价类 + 边界值：
  用户名：2字符(边界外) / 3字符(边界) / 4字符(边界内) / 19字符 / 20字符 / 21字符
  用户名：含中文 / 含特殊符号 / 为空
  密码：5位 / 6位 / 7位 / 15位 / 16位 / 17位
  密码：纯数字 / 纯字母 / 无数字无字母（全特殊字符）
  手机号：空 / 非11位 / 非数字 / 正确格式

场景法：
  基本流：正确填写所有字段 → 注册成功 → 跳转登录
  备选流1：用户名已存在 → 提示"用户名已被占用"
  备选流2：两次密码不一致 → 提示"密码不一致"
  备选流3：验证码错误 → 提示并刷新验证码

判定表：
  考虑"是否勾选用户协议"和其他条件的组合
```

## 二、Bug 生命周期 ⭐⭐

```
        ┌→ 新建(New) ─→ 确认(Open/Assigned) ─→ 修复中(In Progress)
        │                                            │
        │                                            ↓
        │                                      已修复(Fixed/Resolved)
        │                                            │
        │                                            ↓
        └──────────── 重新打开(Reopen) ←── 验证不通过 ← 待验证(To Be Verified)
                                                     │
                                                     ↓ 验证通过
                                                 关闭(Closed)

特殊情况：
  - 拒绝(Rejected)：开发认为不是 Bug → 测试需要沟通/升级
  - 延期(Deferred/Postponed)：确认是 Bug 但本版本不修
  - 重复(Duplicate)：别人已经提过 → 关联到原 Bug
```

### Bug 流转话术

面试官问：「说说你遇到过的 Bug 流转中的冲突，怎么解决的？」

**参考回答**：
> 有一次我提了一个 Bug，开发标记为"By Design"拒绝了。我没有直接争执，而是回去翻了需求文档，找到了对应的 PRD 描述，截图发给开发，并拉上产品经理一起确认。最终产品确认这是一个 Bug，开发修复了。我的体会是：**遇到分歧不要硬刚，用需求和数据说话。**

## 三、如何写好 Bug 报告 ⭐⭐

### Bug 报告模板

```
标题：[模块] 简要描述（一句话说清楚什么操作、什么问题）

环境：
  操作系统：Windows 11 / macOS 14
  浏览器：Chrome 120
  测试环境：测试服 v2.3.1

严重程度：P1 / P2 / P3
优先级：高 / 中 / 低

重现步骤：
  1. 打开登录页面
  2. 输入正确的用户名和密码
  3. 点击"登录"按钮
  4. 观察页面反应

实际结果：页面一直 loading，无法进入主页
预期结果：登录成功，跳转到主页

重现概率：必现 / 5次中3次 / 偶现

附件：截图 / 录屏 / 接口 response / 日志
```

### 写好 Bug 报告的黄金法则

1. **标题一句话说清楚** — "登录按钮点不了" 比 "登录功能有问题" 好 10 倍
2. **步骤可复现** — 别人照你的步骤能重现，这是好 Bug 的唯一标准
3. **一条 Bug 只有一个问题** — 不要一次报多个问题
4. **区分事实和推测** — "点了没反应"是事实，"可能是后端接口挂了"是推测
5. **附上证据** — 截图、录屏、har 包、接口返回，多多益善

### Bug 严重程度 vs 优先级

| | 严重程度 (Severity) | 优先级 (Priority) |
|---|---|---|
| **谁定** | 测试工程师 | 产品经理 + 测试 |
| **含义** | 对系统的影响程度 | 修复的紧急程度 |
| **分级** | 致命/严重/一般/轻微 | 高/中/低 |
| **关系** | 通常严重→高优先，但不绝对 | 如：公司 Logo 错了——不严重但高优先 |
