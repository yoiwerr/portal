# 06 · 测试分类与核心概念

---

## 一、按测试技术分类（必考）⭐⭐⭐

### 黑盒测试 (Black-box Testing)

> 不看代码，只看输入和输出。把软件当"黑盒子"。

- **关注点**：功能是否正确、界面是否友好、输入输出是否符合预期
- **用例设计方法**：等价类、边界值、场景法、判定表、正交表、错误推测法
- **谁来测**：功能测试工程师、业务验收人员

**面试话术**：
> 我日常做的大部分是黑盒测试。优势是贴近用户视角，能发现设计层面的问题；局限是不知道代码内部逻辑，无法判断测试覆盖率是否充分。

---

### 白盒测试 (White-box Testing)

> 看得见代码，基于代码逻辑设计测试。

- **关注点**：语句覆盖、分支覆盖、路径覆盖、条件覆盖
- **手段**：代码走查、单元测试
- **谁来测**：开发人员（单元测试）或测试开发

**常见覆盖率指标**（面试能说 2-3 个即可）：

| 覆盖率类型 | 含义 | 严格程度 |
|-----------|------|---------|
| 语句覆盖 | 每行代码至少执行一次 | 最弱 |
| 分支覆盖 | 每个 if/else 分支都走到 | 中等 |
| 条件覆盖 | 每个条件表达式的真/假都取到 | 较强 |
| 路径覆盖 | 每条可能的执行路径都走一遍 | 最强（组合爆炸） |

**面试话术**：
> 我没有做过系统的白盒测试，但我了解基本概念。比如开发写单元测试时，我会跟他们确认关键逻辑的边界和异常分支都覆盖了。

---

### 灰盒测试 (Gray-box Testing)

> 介于黑白之间——知道部分内部逻辑，但不逐行审查代码。

- **典型场景**：
  - 接口测试：知道 API 的参数校验逻辑，重点测边界和异常
  - 数据库验证：知道写入的表和字段，验证数据落库是否正确
  - 集成测试：知道模块间的调用关系，重点测交互边界

**面试话术**：
> 接口测试就是典型的灰盒测试——我看不到全部代码，但我知道这个接口需要哪些参数、有哪些校验规则、会返回什么字段。我可以针对性地测边界值和异常场景。

---

### 三种测试对比（面试速记）

| | 黑盒 | 灰盒 | 白盒 |
|------|------|------|------|
| 是否看代码 | 不看 | 知道部分逻辑 | 逐行审查 |
| 谁测 | 测试工程师 | 测试/测开 | 开发 |
| 优势 | 贴近用户 | 两者兼顾 | 覆盖率高 |
| 局限 | 不能判断覆盖率 | — | 脱离用户视角 |
| 典型工具 | 手工、Selenium | Postman、SQL | JUnit、pytest |

## 二、按是否运行分类

### 静态测试 (Static Testing)

> 不运行代码，通过**人工审查或工具扫描**发现缺陷。

- **形式**：需求文档评审、设计文档评审、代码走查 (Code Review)、静态代码分析
- **工具**：SonarQube、ESLint、Checkstyle
- **优势**：早期发现，修复成本低

### 动态测试 (Dynamic Testing)

> 运行代码，观察实际输出是否与预期一致。

- **形式**：所有需要执行程序的测试（功能测试、接口测试、单元测试等）
- **优势**：能发现运行时才暴露的问题（内存泄漏、并发问题）

**面试话术**：
> 测试不是"运行程序"才叫测试。需求评审就是静态测试——我们曾经在需求评审阶段发现了一个严重的逻辑漏洞，如果在编码后才发现，返工成本至少是 10 倍。

---

## 三、按测试阶段分类 ⭐⭐

```
单元测试 → 集成测试 → 系统测试 → 验收测试
  (开发)    (开发+测试)   (测试)     (产品/客户)
```

| 阶段 | 测什么 | 发现什么问题 | 谁负责 |
|------|--------|-------------|--------|
| 单元测试 | 单个函数/方法 | 编码错误、逻辑缺陷 | 开发 |
| 集成测试 | 模块间交互 | 接口不匹配、数据传递错误 | 开发 + 测试 |
| 系统测试 | 整个系统 | 功能/性能/安全/兼容性 | 测试 |
| 验收测试 | 业务场景 | 需求理解偏差、业务流程缺陷 | 产品/客户 |

### α 测试 vs β 测试（面试加分项）

| | α 测试 (Alpha) | β 测试 (Beta) |
|------|------|------|
| 场所 | 开发环境 / 内部环境 | 用户真实环境 |
| 测试人员 | 内部员工（非本项目） | 真实用户 |
| 是否有开发在场 | 是 | 否 |
| 目的 | 发现严重 Bug | 收集用户反馈 |
| 版本状态 | 基本稳定，未正式发布 | 接近发布 |

**面试话术**：
> α 测试是内部可控环境的最后一轮验证，β 测试是真实用户的验收——我们日常说的"灰度发布"其实就类似于 β 测试，先放一部分真实用户进去，观察是否有问题。

## 四、测试策略 vs 测试计划 ⭐

> 这一对概念经常被混淆，面试时区分清楚能加分。

| | 测试策略 (Strategy) | 测试计划 (Plan) |
|------|------|------|
| 层次 | 高层方向 | 具体执行 |
| 回答什么 | "怎么测"——整体思路和方法 | "什么时候、谁、测什么" |
| 内容 | 测试类型选择、自动化比例、风险优先级 | 范围、排期、资源、交付物 |
| 制定者 | 测试负责人 + 架构师 | 测试负责人 |
| 变更频率 | 项目级，很少变 | 每个迭代更新 |

**举例对比**：
- **策略**：「本版本重点保障支付链路的正确性，接口层做自动化回归，前端手工探索性测试为主」
- **计划**：「12.1-12.3 测用户模块，12.4-12.6 测订单模块，12.7 回归，12.8 出报告」

---

## 五、探索性测试 ⭐

> 不事先写完整用例，而是**边探索边测试**，依赖测试人员的经验和直觉。

- **和脚本化测试的区别**：
  - 脚本化测试：用例提前写好，按部就班执行
  - 探索性测试：同时进行"学习、设计、执行"三个活动

- **适用场景**：
  - 需求文档不完整时
  - 新功能第一轮测试（先探索再补用例）
  - 时间紧迫时（快速摸清质量状况）
  - 回归测试后补充的"自由测试"时间

**面试话术**：
> 我不会只用一种方法。通常是先做一轮探索性测试快速摸清功能边界和风险点，然后把这些发现写进用例库。正式执行时按用例覆盖，最后再留一些时间自由探索。探索性测试和脚本化测试是互补的，不是对立的。

---

## 六、猴子测试 / 随机测试

| | 猴子测试 (Monkey Testing) | 随机测试 (Ad-hoc Testing) |
|------|------|------|
| 执行者 | 通常是工具/脚本 | 人工 |
| 方式 | 完全随机输入/操作 | 有一定目的但无预先设计的步骤 |
| 目的 | 发现崩溃、内存泄漏 | 发现用例未覆盖的缺陷 |
| 类比 | 一只猴子在键盘上乱敲 | 凭直觉随便点点 |

## 七、软件质量模型 (ISO 9126 / ISO 25010) ⭐

> 面试时如果被问"什么是软件质量"，不要只说"没 Bug"。

**ISO 9126 六大质量特性（背这 6 个词）**：

```
功能性     → 功能是否正确、完备
可靠性     → 系统是否稳定、容错能力
易用性     → 是否好理解、好学习、好操作
效率       → 响应时间、资源占用
可维护性   → 是否好改 Bug、好加功能
可移植性   → 是否能迁移到不同环境
```

**升级版 ISO 25010**（增加了安全性和兼容性）：

```
功能性 → 功能完备性、正确性、适合性
性能效率 → 时间特性、资源利用率、容量
兼容性 → 共存性、互操作性
易用性 → 可辨识性、易学性、易操作性、用户错误保护、界面美观
可靠性 → 成熟性、可用性、容错性、可恢复性
安全性 → 保密性、完整性、不可抵赖性、可追溯性
可维护性 → 模块化、可复用性、易分析性、易修改性、易测试性
可移植性 → 适应性、易安装性、易替换性
```

**面试话术**：
> 软件质量不仅仅是"功能没 Bug"。如果功能正确但响应要 10 秒、界面让用户不知道下一步做什么，那质量仍然是不合格的。我会从功能性、易用性、可靠性、性能这几个最直观的维度去评估一个产品。

## 八、确认测试 vs 回归测试

> 这两个概念面试经常被拿来辨析。

| | 确认测试 (Confirmation) | 回归测试 (Regression) |
|------|------|------|
| 测什么 | 原 Bug 的修复是否正确 | 其他功能是否被修复影响 |
| 范围 | 只测那个 Bug 本身 | 关联模块 + 核心流程 |
| 关系 | 先确认，确认通过后才回归 | 确认测试的后置步骤 |

**面试话术**：
> 开发修了一个 Bug，我首先做确认测试——验证这个 Bug 确实被修好了。然后再做回归测试——检查修这个 Bug 有没有引入新问题。两步都通过，Bug 才能关闭。
