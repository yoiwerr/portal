# 08 · 敏捷测试与专项测试

---

## 一、敏捷开发中的测试 ⭐⭐

### 传统瀑布 vs 敏捷开发

| | 瀑布模型 | 敏捷开发 (Scrum) |
|------|------|------|
| 节奏 | 一个大版本（1-3 个月） | 小迭代 Sprint（1-4 周） |
| 需求 | 一次性确定，变更困难 | 持续调整，拥抱变化 |
| 测试介入 | 开发完成后 | 从 Sprint 第一天就参与 |
| 测试周期 | 专门的测试阶段（1-2 周） | 边开发边测试 |
| 交付 | 所有功能一起交付 | 每个 Sprint 交付可用增量 |

**面试话术**：
> 敏捷对测试最大的挑战是节奏——以前瀑布有专门的测试时间，现在每个 Sprint 2 周，测试可能要压缩到 3-5 天。所以敏捷测试更依赖自动化回归、更依赖风险驱动的优先级排序，也需要测试在需求评审时就更早介入，提前发现需求本身的问题。

---

### Scrum 中测试的角色

```
Sprint 周期（2 周为例）：

Day 1 ─ Sprint Planning
       测试参与：评估测试工作量，提出测试关注点
       输出：每个 Story 的测试估算

Day 1-2 ─ 需求细化
       测试参与：和产品、开发一起细化需求
       输出：Acceptance Criteria（验收标准）

Day 2-7 ─ 开发阶段
       测试：编写用例、准备测试数据、写自动化脚本
       开发自测完提测后开始执行

Day 7-9 ─ 测试执行
       功能测试 + 回归测试 + Bug 跟踪

Day 10 ─ Sprint Review + Retrospective
       测试：演示测试结果、反馈质量问题、提出改进
```

**关键概念**：

| 概念 | 含义 | 测试关注 |
|------|------|---------|
| User Story | 用户故事：一句话描述要做什么 | 测试根据 Story 写 AC（验收标准） |
| Acceptance Criteria | 验收标准：做到什么程度算"完成" | 测试用例的依据 |
| Definition of Done | 完成的定义：代码合并、测试通过、文档更新等 | 测试不通过就不能标记 Done |
| Daily Standup | 每日站会：昨天做了什么、今天做什么、有什么阻碍 | 测试同步进度和阻塞项 |

**面试话术**：
> 我的角色不只是"开发完后来测"。Sprint Planning 时我评估测试工作量，需求细化时我帮产品写出可测试的 AC，开发过程中我准备用例和数据，提测后执行测试。测试是贯穿整个 Sprint 的，不是最后一个环节。

## 二、测试左移 & 测试右移 ⭐⭐

> 这两年非常火的概念，面试大概率会问到。

### 测试左移 (Shift Left)

> **把测试活动提前**——在需求阶段、开发阶段就介入测试。

```
传统：需求 → 开发 → [测试] → 上线
左移：需求 → [测试介入] → 开发 → [测试介入] → [测试] → 上线
```

**左移的实践**：

| 实践 | 说明 |
|------|------|
| 需求评审参与 | 在需求阶段就质疑不合理的设计 |
| AC 编写 | 帮产品写出可测试、无歧义的验收标准 |
| 单元测试 | 推动开发写单元测试，关注覆盖率 |
| Code Review | 参与代码评审，发现潜在的逻辑问题 |
| 静态代码分析 | SonarQube 等工具在 CI 阶段自动检查 |

**面试话术**：
> 左移的核心理念是"缺陷发现得越早，修复成本越低"。需求阶段改一个逻辑问题是 10 分钟，开发阶段改是 1 小时，上线后改可能要 1 天。我现在习惯在需求评审时就认真质疑，因为那里才是质量问题的源头。

---

### 测试右移 (Shift Right)

> **把测试活动延续到上线后**——在生产环境持续验证。

```
传统：需求 → 开发 → [测试] → 上线（结束）
右移：需求 → 开发 → [测试] → 上线 → [监控] → [用户反馈] → [改进]
```

**右移的实践**：

| 实践 | 说明 |
|------|------|
| 灰度发布 | 先放 5-10% 用户，观察无问题再全量 |
| A/B 测试 | 两个版本同时在线，对比数据后选择 |
| 线上监控与告警 | 监控错误率、响应时间、业务指标 |
| 用户反馈收集 | 客服工单、应用商店评论、NPS 调研 |
| 混沌工程 | 主动在生产注入故障，验证系统韧性 |

**面试话术**：
> 右移的核心理念是"测试不可能在发布前发现所有问题，要在线上持续保障质量"。比如灰度发布——如果直接全量上线出了问题就是 P0 事故，但先放 5% 用户，出问题影响范围小，可以立即回滚。

---

### 左移+右移全景图

```
左移（预防）                  传统测试                    右移（持续验证）
←────────────────────────────────────────────────────────────────→
需求评审    单元测试    功能测试    回归测试    灰度发布    线上监控
静态分析    Code Review  集成测试    准出评审    A/B测试    用户反馈
AC编写      持续集成     系统测试    测试报告    告警       混沌工程
```

## 三、TDD / BDD / ATDD ⭐

> 三个概念常被混淆，面试时能区分清楚就是加分项。

### TDD (Test-Driven Development) — 测试驱动开发

```
RED → GREEN → REFACTOR

RED:   先写一个失败的测试
GREEN: 写最少的代码让测试通过
REFACTOR: 重构代码，保持测试通过

特点：开发先写单元测试，再写业务代码
适用：后端逻辑、算法、工具库
```

### BDD (Behavior-Driven Development) — 行为驱动开发

```
Given → When → Then

Given 用户已登录且有 3 件商品在购物车中
When  用户点击"结算"按钮
Then  页面跳转到订单确认页，总金额为 3 件商品之和

特点：用自然语言描述行为，非技术人员也能看懂
工具：Cucumber、Behave、SpecFlow
适用：跨角色协作（产品+开发+测试 共同定义行为）
```

### ATDD (Acceptance TDD) — 验收测试驱动开发

```
先定义验收标准 → 再开发 → 最终用自动化验收测试验证

特点：测试用例=验收标准，在开发前由产品+测试+开发共同确认
适用：需求明确的功能
```

### 三者对比

| | TDD | BDD | ATDD |
|------|------|------|------|
| 谁写 | 开发 | 开发+测试+产品 | 测试+产品 |
| 粒度 | 函数/类 | 功能/场景 | 业务验收 |
| 语言 | 代码（JUnit/pytest） | 自然语言（Gherkin） | 自然语言或 DSL |
| 关注 | 代码正确性 | 系统行为 | 业务需求满足 |

**面试话术**：
> TDD 是开发侧的实践，我作为测试更多参与的是 ATDD——在需求评审时和产品、开发一起把验收标准定清楚，这些验收标准就是后续测试用例的核心。BDD 的理念很好，但我之前的团队没有深度使用过相关框架。

## 四、CI/CD 与测试 ⭐

### 概念速查

```
CI  — 持续集成：频繁合并代码到主干，每次合并自动构建+测试
CD  — 持续交付/部署：CI 通过后自动或手动部署到环境

     推代码 → CI 触发
                 ├── 编译
                 ├── 代码检查（lint）
                 ├── 单元测试
                 ├── 接口自动化测试
                 └── 构建镜像
                       ↓
                   部署到测试环境
                       ↓
                  UI 自动化测试（可选）
                       ↓
              人工确认 → 部署到生产环境
```

**面试话术**：
> 在我之前的项目中，每次提测前 CI 会先自动跑单元测试和接口回归脚本，跑不过就不让合并。这保证了提测版本至少通过了最基础的验证，不会出现"一跑就挂"的低级问题。

## 五、性能测试类型 ⭐

> 面试问到"性能测试怎么做"，不要只说"压一下"。

| 类型 | 目的 | 核心问题 |
|------|------|---------|
| 负载测试 | 测正常/预期负载下的表现 | "1000 人同时下单，响应时间多少？" |
| 压力测试 | 测极限负载，找到系统瓶颈 | "多少并发时系统崩？崩在哪里？" |
| 稳定性测试 | 长时间运行是否稳定 | "连续跑 24 小时，内存会不会涨？" |
| 并发测试 | 多用户同时操作同一资源 | "100 人同时秒杀最后一个库存，超卖吗？" |
| 容量测试 | 测数据量大时的表现 | "订单表 1 亿条时查询还快吗？" |
| 基准测试 | 建立性能基线 | "日常单用户响应时间是多少？" |

### 性能关键指标

```
TPS/QPS    — 每秒处理事务/请求数
RT         — 响应时间（Response Time），含平均/中位数/P95/P99
并发用户数 — 同一时刻在操作的用户数
吞吐量     — 单位时间内处理的数据量
CPU/内存   — 服务器资源占用率
错误率     — 请求失败的比例
```

**面试话术**：
> 我之前没有专职做过性能测试，但了解基本概念。功能测试做完后，对于核心接口（比如登录、下单、支付），我会关注它的响应时间。如果明显变慢，我会提性能缺陷。压测一般用 JMeter 或者 Locust，我们测试环境资源有限，正式的压测会在预发布环境做。

## 六、APP 测试 vs Web 测试 ⭐

> 现在很多岗位要测移动端，这些差异点要能说出来。

| 维度 | Web 测试 | APP 测试 |
|------|---------|----------|
| 兼容性 | 浏览器+分辨率 | 设备型号+系统版本+屏幕尺寸 |
| 网络 | WiFi 为主 | WiFi + 4G/5G + 弱网 + 飞行模式 |
| 安装/升级 | 无 | 安装、卸载、覆盖安装、版本升级 |
| 中断测试 | 无（或少） | 来电、短信、推送、切换前台后台 |
| 手势 | 点击+键盘 | 点击、长按、滑动、多点触控、摇一摇 |
| 权限 | 无 | 相机、定位、通讯录、通知等权限弹窗 |
| 存储 | 无 | 缓存管理、清理数据、SD 卡读写 |
| 电量 | 无 | 耗电量、后台运行 |

### APP 专项测试

| 专项 | 测试内容 |
|------|---------|
| 安装卸载 | 首次安装、覆盖安装、卸载、卸载后重装（数据是否保留） |
| 升级 | 低版本→高版本、跨版本升级、升级后数据完整性 |
| 中断 | 来电、短信、通知栏下拉、闹钟、低电量弹窗、切后台再回来 |
| 弱网 | 丢包 30%/50%、延迟 500ms/2s、限速 2G（用 Charles 或 Fiddler 模拟） |
| 权限 | 首次请求、拒绝后又触发、系统设置中关闭再回来 |
| 横竖屏 | 横竖屏切换后界面是否自适应、数据是否丢失 |
| 多语言 | 系统语言切换后 App 显示语言是否正确 |
| 多设备 | 主流厂商（华为/小米/OPPO/vivo/iPhone）+ 系统版本组合 |

**面试话术**：
> Web 和 APP 测试的核心区别在于**环境复杂度**——Web 测 3-5 个浏览器就够了，APP 要面对几十种设备型号和系统版本的排列组合。另外 APP 要处理各种中断场景，比如正在下单时来了个电话，回来后订单状态不能丢。这是 Web 测试基本不会碰到的。

## 七、小程序测试要点

| 要点 | 说明 |
|------|------|
| 多端表现 | 微信/支付宝/抖音 — 同一个小程序在不同宿主 App 的表现 |
| 版本兼容 | 微信不同版本的兼容性 |
| API 权限 | 小程序 API（获取用户信息、支付、定位）需要授权 |
| 分享 | 分享卡片图片、标题、打开路径是否正确 |
| 分包加载 | 分包是否正常加载，第一次打开速度 |
| 审核 | 小程序有审核机制，提审前要做完整的回归 |
