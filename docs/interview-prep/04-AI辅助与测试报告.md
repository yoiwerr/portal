# 04 · AI 辅助测试 & 测试报告

---

## 一、AI 辅助测试 ⭐⭐⭐

> 这是 JD 里专门提到的一点，面试官很可能会问"你怎么用 AI 提升测试效率"。准备一个具体案例。

### 1. AI 辅助测试用例设计

**传统做法**：拿到需求文档 → 自己从头想用例 → 容易遗漏

**AI 辅助做法**：
```
1. 把需求文档/PRD 给 AI
2. 让 AI 生成初版用例（覆盖多种设计方法）
3. 人工审查和补充（AI 不知道业务上下文，我来补充）
4. 最终输出完整用例集
```

**Prompt 示例**：
> 你是一个测试工程师。请根据以下需求，用等价类、边界值、场景法、判定表分别设计测试用例。
> 需求：用户注册功能，用户名 3-20 字符（字母数字下划线），密码 6-16 位（必须含字母和数字），手机号 11 位必填，需短信验证码。

**面试话术**：
> 我日常会用 AI（比如 Claude/ChatGPT）辅助设计测试用例。做法是把需求文档给 AI，让它先用等价类、边界值、场景法各生成一波用例，然后我来审查——AI 擅长穷举和结构化，但不了解我们的业务上下文和用户习惯，所以我会在 AI 的基础上补充业务场景和异常场景。这样效率比以前纯手工写高很多，而且不容易遗漏。

---

### 2. AI 辅助测试数据构造

**场景**：需要造 100 条订单数据，覆盖不同状态、金额、支付方式

**AI 辅助做法**：
```
Prompt: 请生成 100 条 MySQL INSERT 语句，用于订单表测试数据。
字段：id(自增), user_id(1-50), amount(10-9999随机),
status(pending/paid/shipped/done/cancelled),
pay_method(wxpay/alipay/card),
created_at(最近30天随机时间)

要求：
- status 各状态均匀分布
- 包含边界值：amount=0.01, 9999, 10000
- 包含异常场景：amount 为负数(测后端校验)、status 为非法值(测容错)
```

**面试话术**：
> 造测试数据是一个很费时间的活，特别是要覆盖各种边界和组合。我现在的做法是用 AI 生成 SQL 脚本或 JSON 数据文件，指定好字段、分布、边界要求，AI 几秒就能生成几百条。然后我检查一下合理性，直接导入测试库。比手工一条条写好太多了。

---

### 3. AI 辅助缺陷分析

**场景**：遇到一个复杂 Bug，日志很长，不确定根因在哪

**AI 辅助做法**：
```
1. 把错误日志 + 复现步骤给 AI
2. 让 AI 分析可能的根因
3. 让 AI 给出验证假设的方法
4. 人工验证，确定根因后再提交 Bug
```

**Prompt 示例**：
> 以下是用户登录失败的错误日志和相关接口返回，请帮我分析可能的原因，并给出排查建议。
> [粘贴日志和接口 response]

**面试话术**（关键——展示你是有判断力的）：
> AI 帮我做初步分析，但它不是银弹。AI 推测的根因我会逐个验证，确认了才写到 Bug 报告里。而且 AI 有时候会"一本正经地胡说八道"，必须用实际数据来校验。我的原则是：**AI 给思路和候选原因，我来做判断和验证**。

---

### 4. AI 辅助测试文档编写

| 文档类型 | AI 辅助方式 |
|----------|-------------|
| 测试计划 | 提供模板 + 项目背景 → AI 生成初稿 → 人工调整 |
| 测试用例 | 输入需求 → AI 生成结构化用例表 |
| Bug 报告 | 输入现象描述 → AI 整理成标准格式 |
| 测试报告 | 提供数据和结论要点 → AI 生成完整报告 |

---

### 5. 面试时怎么回答"你用 AI 提升效率"这个问题

**准备一段 2 分钟的答案**：

> 我在日常测试工作中，AI 主要帮我做四件事：
>
> **第一是用例设计**。拿到需求后，我会让 AI 先用等价类、边界值、场景法各生成一版用例，然后我来补充业务特有的场景和异常场景。AI 负责穷举和结构化，我负责判断和补充——效率提升很明显，而且不会遗漏常见的测试点。
>
> **第二是测试数据构造**。比如要造几百条涵盖各种状态和边界的订单数据，以前我手写 SQL，现在让 AI 生成脚本，我检查后直接跑。
>
> **第三是缺陷分析**。遇到报错日志很长的 Bug，我会把日志和复现步骤喂给 AI 做初步分析，它给候选原因，我逐个验证。
>
> **第四是文档**。测试报告、用例文档的初稿都可以让 AI 生成，我润色和补充。
>
> 但我的原则是：**AI 是工具，不是替代我判断的**。所有 AI 输出的东西我都会验证，因为 AI 不了解我们的业务流程，它可能漏掉关键的业务场景，也可能给出似是而非的分析。

## 二、测试报告 ⭐⭐

### 测试报告结构

```
1. 报告概述
   - 测试版本、测试时间、测试范围
   - 测试人员

2. 测试执行情况
   - 计划用例数 / 实际执行数 / 执行率
   - 通过数 / 失败数 / 阻塞数 / 通过率
   - 按模块分解

3. 缺陷分析
   - 新增 Bug 数 / 已关闭数 / 遗留数
   - 按严重程度分布（P0/P1/P2/P3 饼图）
   - 按模块分布
   - Bug 收敛趋势（每天新发现 vs 每天关闭）

4. 风险与问题
   - 遗留的已知问题及影响评估
   - 未测到的模块/场景及原因
   - 测试阻塞项

5. 质量评估与建议
   - 是否可以发布？（对准出标准逐条判断）
   - 如果发布，已知风险是什么？
   - 改进建议

6. 附录
   - 用例执行明细
   - Bug 列表
```

### 面试话术

> 测试报告的核心不是罗列数据，而是**给出质量评估和风险判断**。我写报告会重点回答三个问题：第一，这版本能不能发；第二，不能发的话卡在哪；第三，能发的话遗留哪些风险。数据只是支撑这些结论的。

## 三、版本提测与准出评审 ⭐

### 提测流程

```
开发自测通过 → 提交提测邮件/消息 → 测试接收检查 → 开始测试
```

**提测邮件/消息要素**：
- 版本号、分支
- 本次改动点（新增/修改/删除）
- 自测结果
- 已知限制
- 部署环境信息

**测试接收检查（测试的第一道防线）**：
- [ ] 冒烟测试通过了吗？
- [ ] 部署成功了吗？环境配置对吗？
- [ ] 提测内容描述清楚了吗？
- [ ] 有阻塞测试的已知问题吗？

### 准出评审会

> 准出评审是版本发布前的**最后一关**，测试工程师是质量把关人。

**测试在评审会上要说的**：

1. **用例执行结论**：执行率 100%，通过率 XX%
2. **Bug 结论**：无 P0/P1 遗留，P2 修复率 XX%，遗留 P3 有 X 个（列出）
3. **风险评估**：哪些模块变更风险高、哪些场景没覆盖到（为什么）
4. **准出建议**：建议发布 / 建议延期（给出理由）

**准出标准清单（Checklist）**：

| 检查项 | 标准 |
|--------|------|
| 用例执行率 | = 100% |
| 用例通过率 | ≥ 95% |
| P0/P1 Bug | 全部关闭 |
| P2 Bug 修复率 | ≥ 95%，遗留的 P2 要有规避方案 |
| 回归测试 | 通过 |
| 兼容性 | 目标平台验证通过 |
| 性能 | 无严重退化 |
