## 一、什么时候追问

```python
def route_after_planner(state):
    plan = state.get("plan", {})
    clarify_round = state.get("clarify_round", 0)
    if not plan.get("is_complete", False) and clarify_round < max_clarify_rounds:
        return "clarify"
    return "engineering_check"
```

**触发条件**: `is_complete == False` **且** `clarify_round < max_clarify_rounds`（默认 3）

## 二、追问生成的优先级

追问不是随机问，而是按**风险优先级**排序：

```python
PRIORITY = [
    "goal",          # 目标不清晰 — 最高风险
    "scope.out",     # 边界为空 — 最大风险信号
    "scope",         # 范围
    "scope.in",      # 具体内容
    "constraints",   # 硬约束
    "risks",         # 风险
    "acceptance",    # 验收标准
    "deliverables",  # 交付物
    "permissions",   # 权限
]
```

## 四、追问消息的格式化

追问消息包含两部分：**肯定已完成** + **追问缺失**。

```markdown
了解。以下信息已记入任务契约：
- ✅ 目标已明确：为博客项目添加用户名+密码登录
- ✅ 范围已确定：注册、登录、session 保持
- ✅ 约束已记录：React+TS；下周五前完成

再确认几个细节：

**1.** 有什么是确定不在这次范围内的？定好边界不会跑偏。
  _比如：不需要邮箱验证、不需要权限管理_

**2.** 做到什么程度你觉得算完成？有没有具体的验收标准？
  _比如：密码错误提示不区分具体原因_

（契约完整度 65%）
```

```python
def _format_clarification_message(questions, completeness, rag_context, contract):
    lines = []

    # ── 先肯定已明确的部分 ──
    if contract:
        goal = contract.get("goal", "")
        scope_in = contract.get("scope", {}).get("in", [])
        constraints = contract.get("constraints", [])

        if goal or scope_in or constraints:
            lines.append("了解。以下信息已记入任务契约：")
            if goal:       lines.append(f"- ✅ 目标已明确：{goal}")
            if scope_in:   lines.append(f"- ✅ 范围已确定：{', '.join(scope_in)}")
            if constraints: lines.append(f"- ✅ 约束已记录：{'；'.join(constraints)}")
            lines.append("")

    # ── 根据完整度选择语气 ──
    if progress_pct < 40:
        lines.append("还差一些关键信息，请帮忙补充：\n")
    elif progress_pct < 70:
        lines.append("再确认几个细节：\n")
    else:
        lines.append("最后确认：\n")

    # ── 列出问题 ──
    for i, q in enumerate(questions, 1):
        lines.append(f"**{i}.** {q['text']}")
        if q.get("hint"):
            lines.append(f"  _{q['hint']}_")
        lines.append("")

    lines.append(f"（契约完整度 {progress_pct}%）")
    return "\n".join(lines)
```

## 五、追问后的流程

```
clarify_node 执行:
  1. 从 plan.contract.missing_fields 生成追问
  2. 格式化追问消息
  3. return {"output": output, "clarify_round": clarify_round + 1}

graph 流转:
  clarify → END  (直接结束，等待用户回复)

下一轮:
  用户回复 → router → planner (clarify_round=1)
  planner 重新评估完整度 → 够了: engineering_check / 不够: clarify (round=2)
```

## 六、追问上限

```python
max_clarify_rounds = 3  # 可从 config 覆写

def route_after_planner(state):
    if not plan.get("is_complete") and clarify_round < max_clarify_rounds:
        return "clarify"
    return "engineering_check"  # 超限也进入工程检查
```

> 3 轮追问后即使信息不完整，也强行进入工程检查。防止无限追问。

## 八、与旧版追问的区别

| 方面 | 旧版 (V1) | 当前版 (V2+) |
|------|----------|-------------|
| 问题来源 | 硬编码正则模板 | contract.missing_fields 动态生成 |
| 排序 | 固定顺序 | 风险优先级排序 |
| 模板 | 每种维度 1 个模板 | 每种维度多模板，按轮次轮换 |
| 肯定已完成 | 无 | 显示 ✅ 已记录的信息 |
| 去重 | 无 | 跳过已在 expressed_dimensions 中的 |

---

## 九、关键要点

1. **追问基于 missing_fields** — 不是猜，而是 Planner 明确标记了哪些字段缺失
2. **风险优先** — goal > scope.out > constraints > ... > permissions
3. **先肯定再追问** — 用户不觉得被审问，而是被引导
4. **上限保护** — 3 轮后强制执行，防止死循环
5. **追问也计入上下文** — 追问消息保存在 sessions 中，ContextEngine 会更新 L2/L3
