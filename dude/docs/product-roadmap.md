# dude 逐步优化路线

基准：[产品定义](../PRODUCT.md)，确认日期 2026-10-09。

先做好「新手的想法 → 可交给编程 Agent 的完整方案」，不一次性重写整个工程。下文记录阶段目标与当前状态，不代表全部功能已经完成。

后续执行以 [板块划分](product-modules.md) 为单位，一次只改一个板块。00 流程编排先清理节点职责与连接；01 澄清、02 默认推荐、03 方案生成与检查、04 界面导出是产品主线；05 会话、06 知识模型、07 账号管理、08 配置运维按具体问题分别处理。阶段描述用于目标对照，不再把多个板块打包成同一轮改动。

## 当前状态

文档基线已建立；第一轮已调整实际对话链路：统一规划入口、通俗提示词、核心信息判断、非核心默认兜底、明确要求与假设分开保存，以及只生成文案的方案节点。

已增加离线回归验证和整篇方案检查。结构或内容检查失败会重试，仍失败返回错误，不宣称交付完成；普通解释不会把整个项目会话标为已完成。现有契约 JSONB 记录新增来源字段，使用同会话版本，不需要新增数据库迁移。

数据库、认证、模型接入与检索继续使用现有基础。旧工具和技能实现留存但不绑定到方案生成节点，00 首轮已移除图内空工程检查节点及不可达的多 Agent 分支，Planner 直接进入追问或文案生成；现有进度事件保持兼容。记忆实现、界面、聊天记录导出与交接卡尚未重做。本轮不更新依赖、不部署。

测试使用确定性替代模型，尚不能证明真实模型每次都能通俗沟通、可靠选择技术或满足语义要求。00 首轮保留现有检索与两层审核策略，新增实际节点序列和重试上限回归；下一块为 01 的提问与真实案例试聊，再逐块调整默认推荐、交付和界面。

工程待核对：Python 配置读取 `PG_*`，现有子项目 Compose 注入 `DB_HOST`、`DB_PORT`、`DB_NAME`；dude-admin 直接运行仍有弱配置默认值。这些是检查现有配置发现的问题，不在本轮改动中修复，后续运行验证需单独处理。

## 第一阶段：身份、语言与执行边界

状态：首轮实现及离线分支验证完成，真实模型效果待验证。

审查提示词、路由和技能入口，让默认对话围绕新项目方案。移除或限制代码生成、代码审查、接管执行等面向用户的旧承诺；保留必要的内部检索和规划。

验收：

- 输入「我想做个读书记录网站」，先围绕使用场景沟通，不先让用户选框架。
- 解释术语时有普通语言与具体例子，说明选择对使用、成本或维护的影响。
- 用户要求代码、实际修复报错或改造旧项目时，清楚说明范围，提供范围内的下一步方案。
- 不输出代码或可执行配置，不调用工具改用户项目。

## 第二阶段：澄清与默认兜底

状态：核心信息与默认来源处理已实现。具体技术组合仍由模型按场景推荐，尚未建立经过真实案例评估的默认方案库。

整理核心必知信息和可默认细节，区分「用户已确认」「推荐默认」「非阻塞待定」。准备少量小规模场景的默认方案，避免大型技术栈菜单。

验收：

- 用户说「不懂，按最简单的来」后，采用有理由的默认值，继续推进。
- 有足够信息时停止追问；核心目标有歧义、费用或权限存在关键冲突时继续澄清。
- 用户明确需要多人使用时，不擅自降级成仅个人使用。
- 过大范围得到分期建议，核心功能删减由用户确认。
- 不因简化而丢掉持久化、访问控制或必要备份。

## 第三阶段：一份完整方案及导出

状态：十章方案文案和校验已接入对话链路；直接导出方案待实现，当前导出仍是聊天记录。

统一方案结构，评估现有 TaskContract、Markdown 导出和交接卡能复用的部分。内部契约可以辅助规划，最终文档必须满足产品定义，不能用旧摘要冒充完整方案。

验收：

- 用户和编程 Agent 使用同一份文案，不再依赖另外一份交接卡。
- 文档脱离聊天后仍有完整目标、流程、技术建议、数据权限、阶段任务和验收标准。
- 部署、安全、备份、成本与错误处理流程按项目需要写清楚。
- 默认假设有标记，非阻塞待定不会阻碍第一版实施。
- 复制与导出内容一致；没有代码、SQL、可执行配置或脚本。

## 第四阶段：界面与验证

对齐界面用语、方案展示及导出入口，降低「契约」「Agent Panel」等内部术语对用户的负担。先修影响理解与交付的内容，再评估布局调整。

围绕个人读书记录、小型预约工具、公开展示网站等代表性新项目建立对话与交付案例，并增加信息模糊、用户不懂技术、范围冲突和权限需求的检查。验证按行为和交付结果进行，避免只检查固定关键词。

验收：新手能理解推荐理由与下一步；同一想法的方案内部一致；完整交付能指导编程 Agent 开始实施；当前认证与持久化行为没有回归。

## 暂不实施

- 已有项目改造：之后单独整理现状收集、约束识别与变更方案流程。
- 后续方案修改：先调研项目记忆与用户提供上次方案的取舍，再确定交互和数据设计。
- 自动编码、真实报错诊断、代替用户执行或部署：不属于已确认产品范围。
- 无明确需求的基础设施重写或依赖全量升级。

## 每轮交付规则

每次围绕一个阶段或一个清晰问题改动，写明行为变化、验证结果和仍未实现的目标。产品定义改变时先同步文档，运行行为改变时同步测试；不把历史实现当成新需求。
