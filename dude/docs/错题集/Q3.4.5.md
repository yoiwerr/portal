# Q3.4.5 _fallback_plan 什么时候触发，用什么判断完整度

> **状态**：？？？ | **考点**：区分"LLM 抛异常"和"JSON 解析失败"

## 正确答案

`_fallback_plan`（`graph.py:1042`）只在 **LLM 调用抛异常**时触发（网络错、模型挂了），不是"JSON 解析失败"——那走的是 `_parse_planner_json` 的第 4 层兜底。

它用**消息长度**当完整度代理：
- `<20` 字 → `is_complete=False`，追问"能详细说说吗"
- `20~100` 字 → `is_complete=False`，追问"具体要求"
- `≥100` 字 → `is_complete=True`，直接执行

## 关键解析

为什么用消息长度？因为 LLM 挂了，代码手里只剩"用户说了多长"这个最便宜、最不用理解语义的信号。核心假设是"说得越长，信息越完整"——很粗糙，但能让流程继续往下走（要么追问、要么执行），不死掉。

## 面试一句话

> _fallback_plan 只在 LLM 调用抛异常时触发，不是 JSON 解析失败那条路。它用消息长度当完整度代理——短就追问、长就执行——因为 LLM 挂了代码只剩这个最便宜的信号，目的是保证流程不崩。
