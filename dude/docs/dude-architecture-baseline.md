# dude 架构基线

状态：已确认的目标设计，2026-10-27。

本文记录 dude 下一阶段的架构基线。它描述目标架构和迁移边界，不表示所有目标模块已经实现。

2026-10-28 实施进度：第一阶段位于 `dude-orchestrator/`，已实现独立服务、Brief/生成任务/文档对持久层和实验项目 API。实际表名使用 `dude_` 前缀，独立 `dude_orchestrator_migrations`，复用当前 Go 认证所在数据库；下方无前缀名称表示逻辑实体。聊天表、Pi、Wiki 在线适配和新网页尚未实施，默认流量仍走 Python。运行及验证见 [第一阶段说明](../dude-orchestrator/README.md)。

## 产品边界

dude 帮用户把一个模糊想法整理成一份可以交给编程 Agent 执行的技术方案，以及一份可以让项目发起者启动并体验 Demo 的操作手册。dude 不生成项目代码，不替用户维护项目，也不做部署运维和正式验收。

“信息足够”的最低条件是能够说清 Demo 的一条核心链路：**用户做什么，以及会看到什么结果**。用户画像、技术栈、平台和部署方式不是硬门槛；缺少时使用有标记的默认值。

## 目标架构

```text
浏览器
  -> Nginx / dude 路由
  -> dude TypeScript API
       -> Pi Agent Runtime（受限，无文件和 Shell 工具）
       -> 只读 LLM Wiki
       -> OpenAI 兼容模型中转站
       -> PostgreSQL
  -> 现有 Go 登录与管理员服务
```

dude 自身默认使用 React + Vite + TypeScript 前端、Node.js 22 + Fastify API、Pi 的 `pi-agent-core` / `pi-ai`、PostgreSQL 和 Docker Compose。Go 服务继续负责登录、角色和管理员用量能力。新项目的技术方案不强制套用 dude 自己的技术栈：先判断项目类型，适合 Web 时采用 Web 默认方案，不适合时换技术并用口语说明原因。

在线 Agent 不启用 Pi 的编码工具、文件读写、Shell、网络抓取或代码执行能力。它只能读取当前 Brief、查询已发布 Wiki，并返回结构化分析或文档内容。

## Project Brief 是唯一事实来源

每个用户可以有多个项目，一次对话只属于一个项目。项目保存一份可编辑草稿；正式生成时把草稿冻结成不可变版本。修改旧方案时，从当前版本复制出新草稿，生成线性的新版本，不做分支和合并。

Brief 字段至少包含：项目想法、核心 Demo 行为、目标结果、范围、约束、平台、技术选择、数据需求、隐私风险和默认项。每个字段同时保存来源状态：

- `user_stated`：用户明确说过；
- `defaulted`：按小规模默认方案补全；
- `agent_suggested`：专题分析建议，尚未成为用户事实；
- `unresolved`：仍需要用户决定。

聊天记录只用于延续对话，不替代 Brief。用户通过口语修改 Brief，状态面板只读展示“已确定、按默认补全、还需决定”三类信息。

## 数据与版本

关系字段负责身份、归属、版本号和状态，Brief 内容放在可演进的 JSONB 中。目标表如下：

- `projects`：项目身份、用户归属、当前草稿引用和当前版本；
- `brief_drafts`：可编辑 Brief JSONB、字段来源和更新时间；
- `brief_versions`：生成时的不可变 Brief 快照、结构版本和 Wiki 版本；
- `conversations` / `conversation_messages`：项目对话；
- `artifact_versions`：同一 Brief 版本下的技术方案和 Demo 操作手册；
- `generation_runs`：生成任务状态、模型配置摘要、错误类别和重试信息，不保存完整模型请求日志。

一份交付版本必须同时有技术方案和操作手册，且两份文档引用同一个 `brief_version_id`。任一文档生成失败时，保留草稿和失败运行记录，不把半成品标为可交付；上一份成功版本继续可读。

第一阶段只读展示文档，提供复制和 Markdown 下载。用户想修改时回到对话并生成新版本。

## Agent 编排

主协调器是唯一可以合并和更新 Brief 的组件。它按当前 Brief 选择最多 2–3 个专题 Agent 并行运行；专题 Agent 读取同一份 Brief 快照，不直接改数据库、不直接向用户提问。

专题注册表先提供产品范围、交互流程、技术方案、数据与隐私四类专题。每个专题都返回统一结构：发现的问题、建议、依据、来源状态、是否需要用户决定、对 Demo 范围的影响。主协调器负责去重、处理冲突，并把真正需要决定的内容合并成一轮口语问题。

核心 Demo 行为明确后，主协调器可用默认值补齐次要信息，并提示用户点击“生成方案”。正式生成不会自动触发。生成过程采用同一 Brief 快照，先生成技术方案，再生成操作手册。

Pi 只负责模型运行、流式事件和受限工具边界；调度、结构化校验、版本提交和重试由 dude 自己负责。`pi-durable` 暂不作为生产持久层，避免把实验性存储与 PostgreSQL 事实模型混在一起。

## LLM Wiki

LLM Wiki 是只读的建议来源，不是项目事实来源。在线请求只读取已经发布并带版本号的 Wiki，不联网抓取、不在线编译、不在线发布。技术建议应附通俗理由和 Wiki 依据；用户明确说过的内容优先于 Wiki 建议。

没有合适 Wiki 内容时，可以使用明确标注的默认方案，不能把模型猜测写成官方事实。技术方案记录生成时使用的 Wiki 版本，保证历史文档可追溯。

## 用户流程

1. 用户新建项目，用口语描述想法。
2. 主协调器更新草稿，必要时并行调用专题 Agent。
3. 页面展示 Brief 状态；主协调器只集中询问影响 Demo 的问题。
4. “用户动作 → 可见结果”明确后，次要字段按默认值补齐。
5. 用户点击生成，系统冻结 Brief 版本并生成两份文档。
6. 用户查看、复制或下载技术方案和 Demo 操作手册。
7. 用户继续修改时创建下一份线性版本，旧版本只读保留。

## 隐私与运行边界

项目内容、Brief、聊天和文档默认保存在用户项目中；用户可以删除整个项目。相关内容会发送给配置的模型中转站，dude 不把请求内容另存为训练数据或额外永久副本。运行日志只记录状态、耗时、错误类别和关联 ID，不记录完整对话内容。

服务端只配置一个默认模型和 OpenAI 兼容地址，页面不提供模型选择。密钥使用环境变量，不进入 Brief、文档、日志或前端。

## 迁移路线

1. 新建 TypeScript `dude-orchestrator`，先完成 Project Brief、版本、文档和 generation run 数据模型。
2. 用 Pi 完成单协调器主链路，先不启用并行专题。
3. 接入只读 LLM Wiki，生成成对文档并做结构化校验。
4. 增加固定专题注册表和最多 2–3 个按需并行任务。
5. 通过新 API 路径或内部开关，在现有 Python 服务旁验证真实网页流程。
6. 新链路稳定后，将 `/dude/api/chat/...` 切换到 TypeScript，保留 Python 回退窗口。
7. 完成数据、权限、日志和部署验证后，再移除旧 Python 编排代码。

每一步都保持现有登录、管理员、数据库和旧路径兼容；迁移期间不重建已有数据库，不让两套服务同时写同一份新版本状态。

## 明确不做

- 不让 Agent 写代码、执行命令或直接操作用户项目；
- 不把所有专题 Agent 的输出直接展示成互相矛盾的对话；
- 不把用户画像设为生成门槛；
- 不在第一阶段做分支合并、多人协作、模型选择、维护流程、部署运维和正式验收；
- 不为了“统一技术栈”给明显不适合 Web 的项目强行使用 React。
