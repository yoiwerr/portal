# dude 产品定义

确认更新：2026-10-28。本文与 [架构基线](docs/dude-architecture-baseline.md) 记录已确认的目标；旧教程、旧提示词或运行实现与本文冲突时，不得反过来扩大产品范围。实际迁移进度见 [模块地图](CLAUDE.md) 和 [新服务说明](dude-orchestrator/README.md)。

## 定位

dude 帮没有开发经验的人，把一个新项目想法聊成可以交给编程 Agent 实施的方案。用户不需要先理解框架、数据库和架构名词；dude 用日常语言解释实际选择，推荐简单、小规模的默认方案。

最终交付两份 Markdown 文案：**给编程 Agent 的技术方案**和**让用户启动并体验 Demo 的操作手册**。dude 不生成代码、不制作原型、不执行用户项目；操作手册不延伸到维护和正式验收。

## 什么信息够用

最低条件是一条明确的核心 Demo 链路：**用户做什么 → 会看到什么结果**。用户画像、技术栈、平台和部署偏好不是必答问卷，缺少时采用有来源标记的简单默认值。

会改变核心行为、权限、数据处理或不可接受费用的矛盾需要集中说明；互不影响的问题可合并询问。其余细节按推荐推进，避免逐轮追问。信息够用后提示用户明确发起生成，不自动冻结或发布。

## 对话和默认规则

1. 说口语，用具体场景解释功能；技术名词只在有助于用户理解取舍时出现。
2. 给案例和推荐，说明对体验、费用和操作难度的影响，不让小白凭感觉乱选。
3. 用户说不懂、随便、按推荐时，采用最小可行默认方案，不重复卡住流程。
4. 不偷改用户明确要求。必要取舍集中说明，核心范围变化需要用户决定。
5. 技术选择根据项目类型，不强行把所有项目做成 dude 自己使用的 Web 技术栈。
6. 默认值不能降低数据安全、权限和持久化要求，也不能伪装成用户已确认的事实。
7. 不接手真实报错的诊断修复；可以给用户一份交给编程 Agent 的排错处理建议。

## 项目事实和修改

Project Brief 是唯一项目事实来源，聊天历史用于延续交流。字段保留 `user_stated`、`defaulted`、`agent_suggested`、`unresolved` 来源；模型建议不会自动冒充用户要求。

每个用户可建立多个项目，聊天属于项目。用户通过对话修改草稿，状态面板只读。明确生成时冻结不可变 Brief 版本，两份文案来自同一版本且一起发布；任一失败不展示半份成功交付，上一成功版本仍可读。

修改继续沿当前项目生成线性新版本，历史只读；首版没有分支合并和多人协作。项目保存至用户删除，删除同时移除关联资料和文档。

## 两份交付物

技术方案必须能够独立交给 Codex 等编程 Agent，不依赖隐藏记忆或旧聊天。覆盖核心目标、Demo 范围、操作流程、技术选择及理由、数据归属和权限、实施顺序、必要约束、默认假设及待定事项。说明希望实现的行为，不输出项目代码、伪代码、SQL 或可执行配置。

操作手册面向项目发起者，用口语说明需要准备什么、把技术方案交给 Agent 后怎么配合、如何启动项目、从哪里进入并体验核心 Demo。执行细节应与技术方案一致，不凭空编造未生成项目的实际路径或命令。到能体验 Demo 为止，不增加生产维护、持续运营和正式验收流程。

质量检查是 dude 内部的文案一致性与可用性检查，不等于替用户执行项目或承诺已验证代码。dude 不提供原型，实际 Demo 由后续编程 Agent 构建。

## 技术机制的边界

Pi 只负责受限模型运行；主协调器是 Brief 唯一写入者。必要时按固定注册表选择最多 2–3 个专题并行分析，专题只返回建议，不直接向用户提问或写事实。

LLM Wiki 是版本化、已发布、在线只读的建议来源，来源编译和发布在线下独立进行。不重新引入在线向量 RAG，不给 Agent 文件、Shell、网络抓取或执行用户项目的工具。

服务端固定一个模型配置，不向小白提供模型选择器。项目内容会发送给配置的模型服务；运行日志不保存完整内容，不建立额外永久请求副本，不用于训练。

## 当前实施和暂缓项

第一阶段 `dude-orchestrator/` 仅有服务/数据基础和认证项目 API；网页仍走旧 Python 链路。两份文档的真实模型生成、Pi、Wiki 适配和新前端继续分阶段落地，不能宣称这些已经上线。

首版不支持已有项目改造、分支、多用户协作、代码执行、代部署、维护或正式验收。已有项目改造需要以后单独设计流程。

界面应简单清楚，以中文内容和对话为主；Brief 状态与文档只读查看，支持后续复制和 Markdown 下载。少用装饰、大色块和技术术语；以 WCAG AA 为目标，尊重减少动画偏好。
